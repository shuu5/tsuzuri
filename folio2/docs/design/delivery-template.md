- 状態: **発効**（総点検の設計ノート `docs/design/audit-2026-09-23.md` の §3-b の P3 と、持ち主の承認 2026-09-23 08:13 JST・対話面 R-8・逐語「問いは全部推奨で」・裁定 id = f2-648 notes 2026-09-23 08:13 JST）。
- 何のための文書か: 便 105 以降の契約（`docs/design/delivery-<N>.md`）を、毎回同じ骨で書くための型。**規則は置かない**（P-5.4・N-2.1）。ここが定めるのは「どの節をどの順で置くか」と「必ず書く 4 点」だけで、機械が執行する規則は規則の表の行（D-13 ほか）が持つ。
- 雛形の出所: `docs/design/delivery-104.md`（便 104・2026-09-23 着地）。節の並び・契約表の欄・断りの字は、その 1 本を骨にして起こした。数の書き方だけが違う（§3 の (a)）。
- 置き場: この文書は folio2 の設計ノート。席が保守し、契約の作法が変わったら上書きする。履歴は版管理が持つ。

## 1. §0 — 表題の下の箇条

契約の冒頭は、表題（`# 設計: 便 <N> — <1 行の題>`）の直後に置く箇条の並びである。行の名は次の 7 つで、要らない行は落とす。

| 行 | 中身 |
| --- | --- |
| 要件 | この便が当たる要件の id と、その要件の版（例: `FR20`（天井の門・第 1.29 版）） |
| 条 | 根拠の条の id と規範文の要旨。判断の材料になる条だけを挙げる |
| 出所 | なぜこの便が要るか。実測した 1 行（命令と出力と終了コード）か、天井の所見の id か、持ち主の逐語を引く |
| 置き場 | 「この文書は folio2 の設計ノート。契約表は末尾の区間。審査の材料は行 `db` が指す §1 だけ」の断り。write-set の書き方（新しい file の `+`・縮む file・新しい dir の有無）もここに書く |
| 門 | 天井の門（`folio ceiling --gate`）の結果と、その便が門の対象かどうか。対象外なら断りの字をそのまま引く |
| 前の便 | 前提になる便の番号と着地の状態。**base の commit** をここで 1 回だけ名指す |
| 改訂 | 受付の断り・審査・検証役への応答で契約を直したときに、改訂 b・c・d … として 1 行ずつ足す。何を直し、何を直していないか（数値・write-set・歯の本数・`done`・`verify`）を毎回書く |

## 2. §1 以降 — 節の並び

| 節 | 何を書くか |
| --- | --- |
| §1 設計 | 審査が読む唯一の節。判定に要る材料を全部ここに置く。中は (a)(b)(c)… の小見出しで割る。定型の小見出しは、いま起きていること（実測）／直す先とその理由／採らなかった形と理由／歯の土台／歯／凍結 anchor が動くか／大きさ／本便が運ばないものと撤退条件 |
| §2 範囲 | 「入れる」と「入れない」の 2 つの箇条。file・関数・欄の粒度で書く |
| §3 部品 | id・名・役 の 3 列の表。契約表の `title` が指す実体を、この表の id で呼ぶ |
| §4 検査（歯） | §1 の歯の節を指す 1 行と、共通の検証（`.vessel.toml` の common-verify）の名 |
| §5 依存 | 外部 crate の増減・host に要る命令・前提になる着地済みの便・書き換える file が重なる並行の便の有無 |
| 契約表 | `<!-- contracts:begin -->` から `<!-- contracts:end -->` までの区間。手書きの toml |

## 3. 必ず書く 4 点

### (a) 数値は参考値と断る

契約の本文に、要約値（sha256）・byte 数・行数の**実測値を写さない**（規則の表の行 D-13）。書くのは、その値を組み直す手順（独立の script の名と撃ち方）と、変わらないものの理由である。数を挙げるときは「参考値（base `<sha>` の実測）」と断り、測った土台を添える。

理由は、先行の便が着地すると写した数が古くなり、審査の失敗か契約の改訂を生むことである（総点検の棚卸しでは、改訂を持つ契約 24 本・41 回のうち、便の中身の誤りに由来する改訂は無かった）。

凍結 anchor の大きさのように、その便が**動かさないこと**を主張する数は、動かさない理由と、組み直す手順を並べて書く。

### (b) 新設の名は散文で書く

base に無い名（新しい関連関数・新しい定数・新しい file の中の項目）は、`型::項目` の形で名指さない。器の受付は名指しを base の木で解こうとして断る。書き方は「`Round` に足す関連 fn の `split` と `build`」のように、置き場の file 名と項目名を散文で並べる形にする。base に在る非公開の関数も同じで、`gate::sources_digest` ではなく「`gate.rs` の `sources_digest`」と書く。

### (c) 「当たらないもの」の主張には歯を 1 本

§1 の「本便が運ばないもの」や「床も天井の印も門も変わらない」のような、**影響が及ばないという主張**には、凍結の土台（`tests/fixtures/`）でそれを確かめる歯を 1 本付ける。土台がその場合を 1 つも持たないなら、その場合を持つ土台を新しく手で書いてから主張する。

これは便 98 の穴の型である。便 98 の契約は「天井の印も門も変わらない」と書いたが、印の側は「材料の束の写しは全観点で同一」という前の前提を持っており、凍結の土台では 4 観点の写しが偶然そろっていたので歯が拾えず、印が書けなくなった（便 104 で是正）。

### (d) 取り込みの前に受付を撃つ

契約の PR を統合先へ取り込む前に、席が作業ツリーで受付（`pipe preflight --repo <worktree>`）を撃ち、受付の断り（名指しの未解決・余地の不足・write-set の重なり）を先に潰す。これは規則ではなく席の手順で、規則の表の行 D-12 の門と同じ段に置く（門 → 受付の先撃ち → 受付）。

## 4. 契約表の欄

欄の正本は `contracts/schema.toml`（器の `scribe2 contracts schema` の出力・手で直さない）。必須は 6 つ、任意は 8 つである。

| 欄 | 要否 | 形 | 書き方 |
| --- | --- | --- | --- |
| `id` | 必須 | 字 | 台帳の便の列で次に空いている 2 文字。既に使った字を再利用しない |
| `title` | 必須 | 字 | 便の全部を 1 つの段落で述べる。審査はこれと `section` の節だけを読む。引用符 `"` を中に置かない |
| `req` | 必須 | 一覧 | 当たる要件の id。要件が新設されたばかりで契約から指せないなら、§0 の「要件」の行に線を書く |
| `section` | 必須 | 字 | 審査が読む節の番号。`"1"` に固定する |
| `verify` | 必須 | 一覧 | 撃つ命令をそのまま並べる。絞り込みの語を使うなら、その語を関数名の接頭辞に含める |
| `size` | 必須 | 字 | `S` か `M`。触る src それぞれの余地が、その大きさの見積（S は 100・M は 300）を上回ることを §1 の「大きさ」の節で示す |
| `done` | 必須 | 字 | 歯の本数と、各歯が何を数えるかを、`verify` の並びと数が合う形で書く |
| `write-set` | 任意 | 一覧 | 書き換える file。新しい file は先頭に `+` を付ける。減る file は先頭に `-` を付ける。新しい dir は作らない |
| `touches` / `surfaces` / `creates` / `tests` / `also` / `depends` / `classes` / `opens` | 任意 | 一覧 | 使っていない。要るときは正本の欄の決まりを読む |

## 5. 受付の前に席が確かめること

1. 行数は幅 120 で正規化して数える（`wc` の行数ではなく、各行を `ceil(長さ / 120)` で数えた和）。
2. 触る src の余地（上限までの残り）が `size` の見積を上回る。
3. write-set が並行の便と重ならない。
4. `done` が挙げる歯の数と `verify` の行の数が揃う。
5. 床の定数の写しを触る便は、写しを全数で列挙してから write-set に入れる。
6. §1 に引用符 `"` を置かない（契約表の `title` が引用符で括られるため）。
7. §3 の (d) のとおり、取り込みの前に作業ツリーで受付を撃つ。

- 状態: 裁定済み（2026-09-21 08:59 JST・持ち主の逐語「問い１−４は推奨で進めて」・f2-648 notes・対話面 R-8）= 問 1 案 A（印は repo の生成物）・問 2 案 A（厳格・撤退条件 §4）・問 3 案 A（folio の命令 + 席の手順・器への結線は s2 planner へ要望）。次 = 要件書の次の版（FR20・AC18）と便の列（§6）。

## 1. 事実（2026-09-21・main de3ce19）

1. 天井 1 周 = `folio build --write` → `folio ceiling --write`（束 4 観点）→ AI 4 本（opus・各 250k）→ `folio ceiling --refute` → AI（止める 1 件につき 1 本・120k）→ `folio ceiling --check`（3 値）。所要 15〜20 分。1 周目〜11 周目まで席が手で回した。
2. 束の要約値（digest.txt）= 正本の写し（sources/・7 種の文書の YAML）と面の写し（faces/・HTML）を合わせた sha256。所見 file の record.bundle がこれと違えば床がその観点を「まだ分からない」に落とす（ADR-8 決定 (3)）。**設計文書が 1 byte でも変われば束は古い**。面の生成器（src）が変わっても faces が変わり、束は古い。
3. 印の置き場は今は repo の外（~/.local/share/folio2/ceiling/<周>/）。面の名札（`folio build --ceiling <束>`）はその置き場を読む。main の sha と印の対応は台帳の notes にしか無い。器の受付（dispatch）は folio2 の repo しか読まない。
4. 天井の判定の推移: 1〜9 周目 不合格 → 10 周目 忠実さ 合格 → 11 周目 忠実さ・読みやすさ・整合 合格・実態 1 件（反証中）。直しは全部「席の一括（design-intent の PR・持ち主の承認）」か「便（src）」で入った。**是正の PR 自体が設計文書を変える**ので、印はその PR で必ず古くなる。
5. 器の便の受付は `scribe2 pipe dispatch`（intake → review → spawn → gate → land）。折り込める口は、席が dispatch の前に撃つ手順（裁定 1 の「受付の事前読み」）と、vessel の検証の行（.vessel.toml・器の版 b3f5f01 で {threads} の穴を持つ detection-verify）。器の側の結線は ADR-8 決定 (6) のとおり器が決める。
6. 余地: findings.rs 1,069（余地 431）・bundle.rs 501（余地 999）・main.rs 544（余地 956）。新しい file は便で `+` 宣言で置ける（新しい dir は不可）。

## 2. 門が答える問い（何を止めるか）

門の入力 = 便の write-set と main の状態。門の出力 = 3 値。
- **通す**（0）: 便が設計文書（design-intent/ の正本）を書き換えないとき（src・tests・docs/design だけの便）。天井の判定に依らない = ADR-8 決定 (4) は「設計文書の便」だけを止める。
- **通す**（0）: 便が設計文書を書き換え、かつ main の印が「4 観点 合格」で、印が指す正本の要約値が今の main の正本の要約値と同じとき。
- **止める**（1）: 便が設計文書を書き換え、main の印が「不合格」のとき。
- **まだ分からない**（2）: 便が設計文書を書き換え、印が無い・印が古い（要約値が違う）・印に「まだ分からない」の観点が在るとき。器は Questioned 相当で席へ戻す（受付を先に進めない・P-4.1）。
- 席の一括（持ち主が承認欄の逐語で発効する design-intent の PR）は器を通らない = 「持ち主の裁定」の経路（ADR-8 決定 (4) の再開の条件）。門は掛けない。

## 3. 🔴 問 1: 印の置き場（判定の正本を repo に持つか）

- 案 A（推奨）: **印を repo の生成物として持つ**。`folio ceiling --stamp --out <束>` が、周の結果（4 観点の findings.yaml と反証の result.yaml）から決定的に導出して `design-intent/preview/ceiling-stamp.yaml` を書く。中身 = 周の id・観点ごとの 3 値と止めるの反証の結果・正本の要約値（sources だけ）・面の要約値（faces だけ）・束の要約値・起動の記録（モデル・時刻）・読んだ文書の id。手で直さない（P-6.2・folio schema --write と同形）。門も面の名札もこれを読む。是正の PR に同梱して main へ入る = main の sha と印が結び付く。
- 案 B: 置き場は repo の外のまま、器の受付に path を教える。× host 固有の path（規則 D-8 の趣旨・別の machine で判定できない）・main の sha と結び付かない。
- 案 C: git の注釈（notes / trailer）に印。× 器に読み手が無い・push で落ちる・生成物の検査（床）に乗らない。
- 撤退条件: 印の file が 1 周ごとに増える形になって版管理の履歴が読めなくなったら（印は 1 file を上書きする形にするので、そうならない見込み）案を見直す。

## 4. 🔴 問 2: 印の鮮度（設計文書が変わるたびに古くなる問題への答え）

- 事実: 印は正本の要約値に結び付く。是正の PR は正本を変える。**厳格に読むと、印は付いた直後の PR で必ず古くなり、門は「まだ分からない」に戻る**。
- 案 A（推奨・段階 1）: **厳格**。古い印 = まだ分からない = 設計文書を触る便は受け付けない。設計文書を変えたら周を回して印を付け直す（席の手順・15〜20 分）。是正の PR は持ち主の承認で入る（門の外）。運びは今の 11 周と同じ。P-4・P-10.3 に忠実で、例外の口を持たない（N-3）。
- 案 B（段階 2 の候補）: **文書ごとの印**。正本の要約値を file ごとに持ち、変わった文書だけ古いとする。門は「便が書き換える文書に古い印しか無ければ止める」。周も差分で回せる（忠実さ・読みやすさ・実態は変わった文書だけ・整合だけは全体）。実装は bundle.rs の要約値を file 単位にし、findings の record.read（既に在る）で観点ごとに読んだ文書を持つ。× 整合の観点は差分にできないので費用は半分にしかならない・「変わっていない文書の印は有効」の意味の検査は天井の領分（P-3.2）で、床が言い切ってよいか疑わしい。
- 案 C: 猶予（印の後 N 便まで有効）。× 規則の例外機構（N-3.1）。採らない。
- 推奨: 段階 1 = 案 A で門を掛け、周の費用（分・token）を台帳に記帳する。撤退条件 = 設計文書を触る便が 1 週間に 5 本を超え、周の費用が便の費用の合計を超えたら、案 B の設計ノートを起こす（ADR-5 の撤退条件と同形）。
- 面の名札への影響: 面の名札（`folio build --ceiling`）は印の file を読む形に変える。正本の要約値が今と違えば名札は「古い（周 N・日付）」を出す（今は「未実施」か 3 値だけ）。

## 5. 🔴 問 3: 門を folio の命令にするか、器の受付の手順にするか

- 案 A（推奨）: **folio の命令 + 席の手順**。`folio ceiling --gate --dir design-intent --write-set <path>...`（3 値・理由を 1 行）。席が便を dispatch する前に撃つ（受付の事前読み・裁定 1 の字面どおり・mk-run.sh の頭に置く）。器の側への結線は s2 planner へ要望（vessel の検証の行に `folio ceiling --gate --write-set {write_set}` を置ける形か・dispatch first の前に撃つ口が要るか）。folio 側は命令だけを持ち、器の都合で待たない。
- 案 B: 器の受付の手順だけ（folio の命令は作らない・席が `folio ceiling --check` と印を目で見る）。× 判定が席の目に依り、検査で確かめられない（P-15.2 の趣旨・P-3.1）。
- 案 C: 器の側の実装を待つ。× 器の段取り（前の版の置き換えの段 2 の後）まで門が無い。
- 撤退条件: 器が自前の門（vessel の検証の行・intake の口）を持ったら、席の手順は外し folio の命令だけ残す。

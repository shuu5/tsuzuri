### 0.1 何を良くするのか（v3 の軸）

v1 と v2 は「1 周あたりに読む字数」を主な物差しにしていた。**裁定でこれは物差しから外れた。** v3 の評価軸は次の 3 つで、この順。

| 軸 | 意味 | 本ノートでの測り方 |
| --- | --- | --- |
| **① 精度** | 設計文書が道標として正しいか。天井が見つけるべき食い違いを見つけられるか | 過去 23 周の所見のうち、何割が「注意の先」の一覧に入るか（§1.7） |
| **② 手戻り** | 見落として後から直す回数 | 「止める」の所見のうち、注意の先に入らないものの本数（§1.7・撤退条件 1） |
| **③ 実時間** | 周の回数 × 1 周の所要（いま 15〜20 分） | 周の回数（§1.6・§3.4）・全体像を得るまでの時間（§6） |

**字数は副産物として書く。** 減ること自体は良いことでも悪いことでもなく、①②③ を損なわずに減るなら書き添える、という扱いにする。

この軸で読むと、v2 が並べた 3 つの手は性格が分かれる。

| 手 | ① 精度 | ② 手戻り | ③ 実時間 | 字数 | v3 で採るか |
| --- | --- | --- | --- | --- | --- |
| 読む欄まで絞る（無関係な欄を落とす） | 同じか上がる（雑音が減る） | 同じ | わずかに減る | 100% → 39.6% | **採る** |
| 周の引き金で周の回数を減らす | 同じ（引き金を正しく取れば） | 同じ | **大きく減る** | 回数ぶん減る | **採る** |
| 影響集合で**束を切る** | **下がる**（切った先の食い違いを見られない） | 上がる | 減る | 大きく減る | **退ける** |
| 影響集合を**注意の先として添える** | **上がる**（どこを見るべきかを先に渡す） | 下がる | 同じ | **0.7〜0.9% 増える** | **採る** |
| 散文の言及を型付きの欄へ書き写す | **上がる**（§1.7 の実測） | 下がる | 増えない（引き金に数えないので） | 索引が太る | **採る（別の PR で進行中）** |

**v3 の骨は「束を切らない。切るのは無関係な欄だけ。影響集合は束を削るためではなく、AI の注意を向けるために使う」である。**

### 1.4 id の形（床が解く範囲）

`crates/folio/src/refs.rs` の `scan_ids` が拾うのは、前が英数字でもハイフンでもなく後ろが英数字でない位置に現れる次の形だけ。条と規範文（`P-` `A-` `N-` に数字・任意で枝番）・要件書（`FR` `NFR` `AC` `CON` `GOAL` に数字）・規則の表（`R-` `D-` に数字）。**判断の記録の id（ADR-n）は対象外**で、判断の記録どうしの突き合わせは `link.rs` が別に持つ。図の id・設計ノートの文書 id・契約 id も母集団の外。

**節点の id 空間は 3 つに分かれている**（床が解く 3 空間／判断の記録／その他）。索引はこの 3 つを 1 つにまとめる。接頭辞が全部違うので重複は無い。

### 1.7 辺をつなぐと精度が上がる（v3 の中心の実測）

持ち主の問いの後半「リンクとノードの対応をしっかり作り込む」は、v2 の時点では「根本から作り直す」の意味に読んでいた。**実際に測ると、作り直さずに辺をつなぐだけで精度が上がる。**

#### 型付きの辺だけのとき

過去 23 周の所見を、所見の場所の id と、所見の本文が指す id との段で数えた。**その所見を立てるのに要る相手を全部そろえる**数え（増分で立てられるかを測る読み）で:

| 観点 | id の付いた所見 | 2 段以内 | 3 段以上の「止める」 |
| --- | --- | --- | --- |
| 整合 | 88 | 64.8% | 4 |
| 忠実さ | 80 | 75.0% | 1 |
| 読みやすさ | 34 | 79.4% | 0 |
| 実態 | 87 | 73.6% | 5 |

（「最も近い 1 つ」で代表させる緩い数えでは 整合 は 98.9% になる。v1 が「2 段で 100%」と書いたのはこの緩い数えで、しかも旗艦に挙げた例〔2026-09-20 round3 F-2〕は実測すると 3〜4 段だった。）

#### 散文の言及を型付きの辺へ昇格させたとき

来歴（`meta`）と生成区間（`schema`）を除き、囲む節点の id が取れる散文の言及 **800 件**のうち、まだ型付きの辺になっていない対は **258 対**。これを辺に足すと:

| 観点 | 2 段以内（前 → 後） | 3 段以上の「止める」（前 → 後） |
| --- | --- | --- |
| 整合 | 64.8% → **79.5%** | 4 → **2** |
| 忠実さ | 75.0% → **83.8%** | 1 → 1 |
| 読みやすさ | 79.4% → **85.3%** | 0 → 0 |
| 実態 | 73.6% → **85.1%** | 5 → **3** |

**4 観点すべてで精度が上がり、「止める」の取りこぼしが 10 件から 6 件へ減る。**

対価は近傍が太ること。節点 1 つあたりの半径 2 の近傍は **中央値 16 → 49・平均 31 → 52・最大 136 → 166**。

**v2 のように束を切る設計なら、この太りは「読む量が 3 倍」を意味した。v3 は束を切らないので、太るのは注意の先の一覧だけである**（§1.8）。だから辺を増やすことに費用の側の理由で反対する根拠が無くなった。

後ろ 2 つに幅があるのは、起草役と検証役で分類の規則が違うためである（起草役 113 / 95・検証役の組み直し 117 / 93）。恒等式は起草役の数えで 279 = 71 + 113 + 95、検証役の数えで 279 = 69 + 117 + 93 になる。**対の数としては 69 が正しい。**

除外 95 対の内訳: **受け皿の欄が無い 59**（規則の表の行が条以外〔要件・判断の記録・ほかの行〕を指す 33・要件書の項が判断の記録やほかの要件・制約を指す 26）・承認と裁定の来歴 17・版の来歴と先例 10・id の形の例示 4・id の言及ではない 3・反対側からの確認と反証の記録 2。除外の標本 15 対は検証役が 15/15 妥当と判定した。

**足した 69 のうち 18 は検証役が誤りと判定した。** 内訳は 2 つの塊である。① **後ろ向きの辺 12**（その判断が生んだ要件・規則・後の判断を、自分の根拠の欄に書いたもの。日付と、要件の注の「判断の記録 ADR-n 決定」で始まる字面と、規則の行の裁定の欄で機械的に判る）。② **否定文だけを出所にした 6**（「本判断は条文を改訂しないので A-2.3 の対象外」という 1 文から A-2 を根拠に挙げたもの。非該当の明言は依存ではない）。**この 18 は外す**ので、書き写しの確定値と再計測の値は起草役の再報告を待つ。①は受け皿の不足でもある（→ 帰結の欄・§8 の G0-a2）。

**受け皿が無いのは、欄の意味が「条だけ」に閉じているからである。** 要件書の `basis` に判断の記録やほかの要件の id を書くと、面の生成器（`face_srs.rs` の 1028〜1030 行が `ctx.article(&q)` で条として解く）が落ち、歯 29 本が赤になる。制約の行も同じ関数を通る。規則の表の行の `article` も条 1 つを指す単値の欄で、`refs.rs` が行 R-4 の双方向の式の中で読んでいる。**欄の意味を広げるのではなく、別の欄を足すのが筋**である。受け皿の足りなさは 3 つあり、重さが違うので便を 2 本に割る（§8 の G0-a1 と G0-a2）。

| 足りない欄 | 対 | 重さ |
| --- | --- | --- |
| 要件書の項 → 判断の記録 | 14 | S（欄 `adrs`・依存の向きが一定で例外が無い） |
| 要件書の項 → ほかの要件・制約 | 12 | 保留（「撤去の前提」「構造の床に寄せた」など意味が一定でなく、1 つの欄に混ぜると何の辺か機械で言えなくなる） |

再計測（型付きの辺だけ・「指す先が在る所見」を分母・base は main の直近）:

| 観点 | 後付けの前 | 後付けの後（足した id 69・直し前） | 258 対すべてを写せたときの見積 |
| --- | --- | --- | --- |
| 整合 | 63.6% | **69.3%** | 79.5% |
| 忠実さ | 75.0% | **82.5%** | 83.8% |
| 読みやすさ | 76.5% | 76.5%（据え置き） | 85.3% |

## 2. 節点と辺の型

語彙 `design-intent/vocabulary.yaml` に 節点・辺・注意の先 は無い（54 語を実測）。発効するなら語彙に足す。

### 2.1 節点

**節点** = 設計文書の中で id を持ち、1 つのまとまりとして読める単位。欄は 5 つ（id・種類・所属 file・欄の要約値・1 行の題）。

種類は閉じた一覧（条・規範文・規則行・目的・要件・非機能要件・受入基準・制約・判断の記録・設計ノートの節・語・欄の語・天井の観点・天井の節・入口の節・相談の問い・相談の節・要件書の節・憲法の節）。

**この一覧の正本と、辺の型の閉じた一覧の写しを、どの file の生成区間へ導出するか。** v1 は file を名指していなかった。名指さなければ便 G1 の契約の行が書けない。

**推奨（席の判断）**: 索引は導出物なので、正本の文書の生成区間には置かない。**便 G1 が索引の欄の決まりの正本（`design-intent/graph.yaml`）を起こし、その生成区間へ導出する。** この正本は入口の棚と天井の正本の文書の一覧に載るので、その 2 file の版上げが要る。索引の中身そのものは版管理に置かない（毎回組み直す導出物）。

節点の粒は **id を持つ行と、所見の置き場になる節** に取る。理由は 3 つ。

1. 天井の所見は既に「場所」を `{doc, at}` で書いている。§1.7 の実測で、その場所の 6 割強は id で、残りは節の名（語彙の語・天井の観点・要件書の scope）である。**節点の一覧は、所見が置ける場所の一覧と一致していなければならない。**
2. 欄まで細かくすると、辺の端が「どの欄が何の欄に依存するか」になり、いま在る欄からは導けない。持っていない情報を持っているふりをしない（P-4）。
3. file の粒では中央値で 22% の文書が丸ごと古くなる。

**節点にしないもの**: 生成区間（`schema` 節）・`meta`（承認と版の来歴）・凍結 anchor・生成物（`preview/`）。ただし **これらは「周の引き金」には数える**（§3.4）。v1 の「生成区間の変更は床が別に数えており天井の領分ではない」は誤りだった。床が数えるのは生成区間と導出の byte 一致であって、注の中身が実態を偽っていないかは天井の領分である（実測でその場所に「止める」が 4 件）。

### 2.2 辺

**辺** = 節点から節点へ引かれた結び。型は閉じた一覧（P-2.4 と同じ扱い）。**v1 の 9 型に in-article と prose を足して 11 型。**

| 型 | 向き | 出所 | 伝播 |
| --- | --- | --- | --- |
| basis | 要件・判断 → 条・規則行・要件・判断 | `basis` | 使う（両向き） |
| in-article | 規範文 ↔ 条 | 構造 | 使う（両向き） |
| verifies | 受入 ↔ 要件 | `verifies`・`verify.ac` | 使う |
| refs | 要件・節の行 → id | `rules`・`rows.ref`・`rows.req` | 使う |
| amends | 判断 ↔ 条 | `amends.target`・`amended_by` | 使う |
| relations | 条 → 条・要件・規則行・節 | `relations.*` | 使う |
| goals ／ article | 要件 → 目的 ／ 規則行 → 条 | `goals`・`article` | 使う |
| **prose（後付けで型付きの欄へ移したもの）** | 節点 → 節点 | 書き写し先の `basis`・`rules`・`relations`・`refs` | **使う** |
| reads | 観点 → 文書 | `viewpoints.reads` | 観点の読む範囲を決める（節点間の辺ではない） |
| figures | 要件・判断 → 図 | `figures` | 使わない（図は別の正本） |

伝播は**両向き**に行う。条 P-1 が変われば、それを根拠に挙げる要件 FR1 も注意の先に入り、逆も入る。

**prose の型は、書き写した後は普通の辺と区別が付かない**（書き写し先が `basis` なら basis である）。表に別行を置くのは、後付けの出所を記録に残すためで、実装が別の型として持つ必要は無い。

#### 書き写せなかった言及

後付けの後に残る言及（自分の id・承認と版の来歴・説明のための言及・節点に結べないもの）は辺にしない。理由は 3 つ。

1. 履歴は今の依存ではない。辺にすると古い判断の記録 1 本を直しただけで注意の先が全体へ広がる。
2. 向きが無い。`meta.status_note` の中の `FR19` は、依存なのか説明なのか区別できない。
3. 条 N-2 の向きに反する。**散文にしか無い依存が本当に依存なら、型付きの欄に書き写すべきである。だからこそ後付けを先に置いた。**

残った言及は **参考の列** として注意の先の一覧に別立てで並べる。床はそれを数えない。

### 2.3 グラフの正本はどこか

**グラフの正本は設計文書そのもの**（正本 YAML の欄）であり、索引は導出物である（P-6.3）。索引の file を人が書く面は作らない（P-6.4）。索引が組めない状態で注意の先を問われたら「まだ分からない」を返す（P-4.2）。

## 3. 注意の先（v2 の「影響集合」を置き換える）

### 3.1 束を切らない

**v2 は影響集合で束を切る設計だった。v3 はこれを取り下げる。**

取り下げる理由は精度である。束を切ると、切った先に在る食い違いを観点は見られない。§1.7 の実測では、辺を昇格させた後でも「止める」の 6 件が 2 段の外に在る。束を切る設計では、この 6 件は増分の周で立てられない。**目的が精度である以上、見られない範囲を作る設計は採れない。**

**v3 の束** = 床 + その観点が読む文書を、**読む欄まで絞って丸ごと**。切るのは観点が自分で「読まない」と宣言した欄だけである。

### 3.2 注意の先の一覧

束の先頭に、次の 3 つを並べた一覧を添える。

| 欄 | 中身 |
| --- | --- |
| 変わった節点 | 前の周の印との要約値の差。id・種類・file・題・何が変わったか（欄の名） |
| 2 段の近傍 | そこから型付きの辺で 2 段以内に在る節点の id と題 |
| 参考 | 型付きの辺で届かないが、変わった節点の id を散文に含む節点（§2.2） |

**これは「ここだけ読め」ではなく「ここから見ろ」である。** 観点の AI は束の全部を持っているので、一覧の外を読んではいけない理由は無い。問いの文に 1 文を足す: 「一覧に挙がった所から見はじめること。一覧の外で見つけた食い違いも、同じ形で所見に挙げること。」

費用は束の 1% 未満（§1.8）。**字数を 1% 足して、AI が最初に見る所を正しく与える。これが v3 の精度の手である。**

### 3.3 半径は何段か

**束を切らないので、半径は「一覧の広さ」でしかない。狭くても情報は失われず、広くても字数が少し増えるだけである。** v2 が持ち主に上げた 1 点目（半径をいくつにするか）は、これで問いでなくなった。

**推奨は 2 段。** 根拠は §1.7 の実測（辺の昇格後、4 観点で 79.5〜85.3% の所見が 2 段以内に入る）と、3 段に広げると近傍が辺を持つ節点のほぼ全部に届いて一覧が一覧でなくなること。

一覧に入らなかった「止める」は、撤退条件 1 が数える（捨てるのではなく測る）。

### 3.4 周の引き金（実時間はここで取る）

**実時間の節約は 1 周の中ではなく周の回数で取る。** 次のいずれかが変わったときに周を回す。

1. 節点の本文の要約値
2. 生成区間（`schema` 節）と欄の決まりの file の中身
3. 面の生成器（`crates/folio/src/face*.rs`・`site.rs`）と部品目録・様式
4. 実態 の観点についてのみ、実装の証拠（契約表の行・着地の印・歯の名）

1 だけを引き金にすると、§2.1 の 4 件の「止める」を生んだ場所の変更が天井に 1 度も掛からなくなる。

**辺の追加は引き金に数えない。** 関係の欄（`relations`・`basis`・`rules`・`refs`）に id を足すだけの変更は、条文も規範文も平易文も動かさない。**後付けと床の規則が天井を高い頻度で走らせる種になってはいけない**（持ち主の裁定の字面）。辺だけが変わった周では、注意の先の一覧が変わるだけで、観点に問う中身は前の周と同じである。

**この判定は決定的にできる**: 便の差分が、節点の本文の欄（`title`・`shall`・`text`・`plain`・`note`・`what`・`value`・`def` ほか）を 1 つも変えず、辺の欄（`basis`・`rules`・`relations`・`rows.ref`・`rows.req`）だけを変えたなら、引き金にしない。欄の分類は実装の型付きの定数に置き、生成区間へ導出する（便 G4）。

周の回数は加えて **規則の表の行 D-12 の一括**（複数の直しを 1 つの便でまとめる運用）で減らす。これは既に在る運用で、本ノートは変えない。

### 3.5 持ち越しは入れない（裁定 1・確定）

**v1 は「前の周で所見が 0 だった観点は判定を持ち越す」と書いた。v2 で落とし、v3 も落としたままにする。**

条 N-3.1（例外機構）に当たるかどうかについては v1 の主張が正しい。持ち越しは旗でも口でもなく、条件は機械で数えられ、1 byte 違えば効かない。**落とす理由は前提が実測で偽だったからである。**

過去 25 周のうち、束の要約値が 1 byte も違わない 2 周が 2 組ある。

| 観点 | 周 | 判定 | 所見 | 2 周で共通 |
| --- | --- | --- | --- | --- |
| 忠実さ | round18 / round19 | 合格 / 合格 | 5 件 / 3 件 | **7 種のうち 1 種** |
| 実態 | round18 / round19 | 合格 / 合格 | 2 件 / 3 件 | **4 種のうち 1 種** |

**判定は安定し、所見は安定しない。** 持ち越しを過去 23 周に当てると所見の 27.6%（111/402・「止める」3 件を含む）が消える。条件を「その節点が前の周から変わっていない」だけに緩めると 312/402（77.6%・止める 16/26）。**天井の所見の大半は、変わっていない字の上で見つかっている。**

さらに **実態 の観点は節点の要約値では守れない**。束の要約値が同じ round18 / round19 で、round19 の 実態 は「便 76 が main f020259 に着地し `schema.rs` の TARGETS が 5 本になった」ことを根拠に所見を立てている。実態 の入力には実装が入っており、節点の要約値には現れない。

**精度の軸では、持ち越しは所見を 27.6% 失う純粋な損である。** 束を切らない v3 では、持ち越しが無くても 1 周の字数は変わらない（周を回すか回さないかは §3.4 の引き金が決める）。

## 4. 印と門（要件書 FR20 の改訂の範囲）

### 4.1 判断の記録 ADR-8 を狭める改訂である（裁定 3・確定）

**v1 の帰結は「本判断は ADR-8 の決定を 1 つも捨てない」と書いた。これは偽だった。**

- ADR-8 決定 (4) の逐語: 「天井が合格でない間は、folio2 自身の設計文書の便の着地を既定で止め、再開は所見の解消か持ち主の裁定だけとする」。条件は「天井が合格でないこと」だけで、便が何の file を触るかを問わない。
- 要件書 FR20 の規範文: 「印に不合格の観点が在れば 1（止める）」。同じく便の file を問わない。

v3 が門の判定の対象を便の file へ狭めるのは「まだ分からない（印が古い）」の側だけだが、**既定で止める範囲が repo 全体から便の file へ変わるので、決定の範囲の改訂である。**

**判断の記録どうしの改訂を記帳する型付きの欄が無い。** 欄の決まり（`design-intent/adr/schema.yaml`）の `amends` は条を指す欄で、`amends_entry` の必須欄は `target`・`field`・`version`・`previous_text`・`new_text`。床（`link.rs` の `amends_targets`）は `target` が条 id か改訂の範囲の節名であることを求めるので、判断の記録を指す行は今は書けない。散文の注に書くだけでは条 N-2.1 / N-2.2 が禁じる形に近づく。

**そこで、欄の決まりに 判断 → 判断 の改訂の欄を足す便（§8 の G7a）を列に入れる。** 欄の決まりの生成区間の正本は実装の定数なので、`crates/folio/src/adr.rs` の定数の改訂で便 1 本ぶんである。

### 4.2 緩めるのは「印が古い」の側だけ（裁定 2・確定）

v1 は「不合格を出した節点が write-set の file に在るときだけ止める」としたが、実測が示す穴が 2 つある。

**穴 1: 所見の「場所」と「直す先」は別の file にあることが多い。** 過去の「止める」13 件を手で読むと、**少なくとも 6 件は直す先が場所と別の file にある**（round1 F-1 = 場所 ADR-1 / 直す先 `adr/schema.yaml`・round2 F-1 = 場所 ADR-9 / 直す先 憲法 P-5.1・round3 F-2 = 場所 R-8 / 直す先 R-8 か CON5・round4 F-1 = 場所 ADR-10 / 直す先 天井の正本か ADR-11・round19 F-1 = 場所 FR19 / 直す先 `index.yaml` か要件書・round20 F-1 = 場所 FR19 / 直す先 `ceiling.yaml` か要件書）。場所だけを鍵にすると**直すべき file の便がすべて素通りする。**

**穴 2: 周を強制する唯一の仕掛けが外れる。** いまは repo 全体の印が古くなるのでどの便も「まだ分からない」に当たり、周が強制される。不合格も便の file で判定すると「誰も触らない file の不合格が、周が起きないまま残る」経路が開く。

**推奨（確定は持ち主）**:

| 場合 | いま | 推奨 |
| --- | --- | --- |
| write-set に設計文書の正本が 1 つも無い | 通す（0） | 同じ |
| 印が 4 観点とも合格・要約値が今と同じ | 通す（0） | 同じ |
| 印に**不合格**の観点が在る | 止める（1） | **同じ。repo 全体で止める（緩めない）** |
| 印が無い・古い・「まだ分からない」の観点が在る | まだ分からない（2） | **緩める。印に無い節点が在る、または要約値が違う節点が在り、その節点がこの便の write-set の file に在るときだけ 2。ほかの file の便は通す** |

**効きはこちらに在る。** §1.6 の 14/40 回と、直しの PR の後に「印が必ず古くなる」問題は、どちらも「まだ分からない」の側の話である。不合格を緩めても得られるものは小さく、穴 1 と穴 2 の危険だけが増える。

通したときも、**印の古い節点の数と不合格の節点の数を 1 行で出し、台帳 f2-648 へ記帳する口まで持つ**（出すだけでは撤退条件の材料にならない）。

### 4.3 印の中身

印（`design-intent/preview/ceiling-stamp.yaml`・生成物）に **節点ごとの要約値の表**を足す。節点は 285 なので、8 字の要約値と id と種類と file で 1 行 40〜60 byte、表全体で約 16 KB（いまの印は 976 byte）。生成物 1 file の上書きなので、版管理の履歴は行単位の差分として読める（P-6.2）。

### 5.3 v1 の 3 つの誤りと、v3 の形

**誤り 1: 面へ出す便が無い。** 導出物は標準出力か生成物の file に出るだけで、持ち主が読む面には届かない。**注から落として代わりを置かなければ、人に対しては純粋な劣化になる。**

**誤り 2: file の名指しが違う。** 要件書の面を組むのは **`face_srs.rs`**（幅 120 で正規化して 1,385 行・余地 115）であって `face.rs`（1,407・余地 93）ではない。どちらも M の便（300 行）は入らない。v1 の「触らない」は方針ではなく、入らないから触れなかった。

**誤り 3: 3 値が非機能要件を表せない。** NFR1 の「未達である」は便の有無ではなく **規則の表の行 R-1 の閾値に対する測定の結果**である。NFR2 の注（1,561 byte）は「2026-09-21 に未達が解消した」までの来歴。**注が最も長い 2 件が導出の対象外になる。**

**v3 の形**:

1. 3 値（着地・便は在るが印が無い・便が無い）は **機能要件（FR）にだけ当てる**。
2. **非機能要件（NFR）は対象外**とし、注は手書きのまま残すと明記する。
3. **面へ出す便を列に入れる**（§8 の G8）。`face_srs.rs` の余地が 115 行なので、先に割る便（G7b）が要る。
4. 落とす文と残す文が同じ文に同居する（NFR1 の「未達である（2026-09-20 時点・天井の 9 周目の止める所見 実態との整合 F-1・反証 支持）」は状態と出所が 1 つの括弧に入る）。切り分けは「状態の語を含む文は、出所の括弧を残して状態の語だけを『状態は導出物が持つ』へ置き換える」とし、8 件の注について落とす前後の字を便の契約表の行に 1 本ずつ書く。
5. 実態 の観点が読む相手を注から導出物へ替える（天井の正本の版上げを要する）。

## 6. 全体像を安く速く得る

持ち主が「設計文書として最重要」と言った所。**精度（AI が何が在るかを知って始める）と実時間（全体像を得るまでの時間）の両方に効く**ので、v3 も残す。

### 6.1 形と大きさ

`folio graph --digest` が 2 つの表を標準出力へ書く。

```
# 節点（1 行 = id / 種類 / file / 要約値 8 字 / 題 36 字・タブ区切り）
A-1	条	constitution.yaml	e4784b48	消す・外へ出す・使う は確認してから
A-1.1	規範文	constitution.yaml	838bbbe4	既存の文書やデータを消す、外へ出す、外部の道具や鍵を使う（課金を含む）操
...
# 辺（1 行 = 端 / 端 / 型・タブ区切り）
```

| | 行 | byte |
| --- | --- | --- |
| 節点の索引 | 285 | 27,392 |
| 辺の索引（対・後付けの前） | 568 | 約 5,700 |
| 辺の索引（対・後付けの後） | 826 | 約 8,300 |
| 合計（後付けの後） | 1,111 | **約 36,000（35 KiB）** |

設計文書の正本の合計は 550,398 byte なので、**全体像は正本の約 6.5%** で得られる。

### 6.2 CLAUDE.md には載せない

規則の表の行 R-2 は CLAUDE.md の生成区間の本文を 8,000 byte 以下に縛る（実測の余地は 88 byte）。**36 KB は載らない。** 載せようとすれば条 P-14.3 と行 R-2 に反する。

代わりに、`folio hello` に **設計文書が在るときの 1 行** を足す。字は「設計文書 285 節点・826 対。全体像は `folio graph --digest`」。1 行なので非機能要件 NFR1 の母集団（行 R-1）にも収まる。`folio hello` が repo に何も書かない性質（印は `--state` の下だけ・N-1）は変えない。

### 6.3 ここで作らないもの

図は作らない。節点 285・対 826 のグラフの図は人が読めるものにならず、図の型の閉じた一覧（行 R-5・8 型）にも無い型を要求する。持ち主が「全体像」と言ったのは **AI にとっての** 全体像であって、絵ではない。

## 7. 台帳との絡み

**台帳へは書かない。** 台帳は規則を持たない（P-5.4）。読むのは `bd --readonly list --all --json` の出力だけ。

**台帳由来の欄は床の合否と門の判定に使わない。** 台帳は machine-local で版管理の外にあり（remote の実態は `folio2.git` の `refs/dolt/data`）、そこから導く値は端末と同期の時点で変わる。条 P-3.1 は機械で**決定的に**検査できる項目を床に置くと定め、P-10.1 は検査が凍結 anchor を持つことを求める。読めないときは「まだ分からない」で足りるが、**読めるが古いときは「まだ分からない」ではなく違う値を返す。**

```
要件（FR20）
  └─ 契約表の行（delivery-72.md#bu の req 欄）        ← 87 行・181 件  ［版管理の中・床に使える］
       ├─ 着地の commit（Scribe2-Contract の印）       ← 34 commit     ［版管理の中・床に使える］
       └─ 台帳の行（f2-648.107 の設計への案内）        ← 42 件 → 40 行 ［版管理の外・面と知らせだけ］
```

契約が受け付けられた後にその要件の節点が変わったら、**便の側に「要再読」を出す**（席と器への知らせ。止める判断は門が持つ）。台帳の行の依存は作業の順序であって設計文書の関係ではないので、読むのは設計への案内 1 種類だけにする。

#### G0-a1 の中身（実測・base は origin/main）

**受け皿の足りなさは 1 種類ではない。** §1.7 の表のとおり、要件書 → 判断の記録（14 対）は依存の向きが一定で例外が無く、規則の表の行 → 条以外（33 対）は行 R-4 の双方向の式に触る。重さが 3 倍違うので便を割り、**小さく確かな方を先に出して効き目を測る**。

- **欄の名は `adrs`（判断の記録の id だけを受ける）。** 何でも受ける汎用の欄（`refs`）にすると `basis` との使い分けが人の判断になり、機械で数えられる形に閉じるという向き（条 N-2）から遠ざかる。14 対は 14 とも要件の注の 1 文目が「判断の記録 ADR-n 決定 (k)」で始まる＝意味が 1 つに定まる。
- **逆向きでは代わりにならない。** 判断の記録の `basis` に要件を書く形は、1 回目の後付けでも 14 対のうち 5 本しか埋まらず、しかもその 5 本は後ろ向きの辺として外す対象である。
- **閉じた一覧に 1 語足す。** `crates/folio/src/check.rs:126` の `const SRS_ITEM_OPTIONAL: [&str; 3] = ["milestone", "rules", "note"]` を 4 へ。正本は実装の型付きの定数（条 P-5.6）。
- **判定はもう在る。** 同じ file の `check_srs_figure`（709 行〜）が図の行の `refs` を `adr::is_basis_id` で判定しており、受ける id の形は 条・要件・規則の表の行・判断の記録。`adrs` はそれを判断の記録だけに狭めた枝で足りる。
- **面に出す口も在る。** 判断の記録の id を面の行き先に解く関数は `face_srs.rs` の 160〜190 行に在る（`adr-<数>.html` と `adr/<id>.yaml` の存在を確かめる形）ので、新しい解決器は要らない。要件の chip を作る所（1023〜1040 行）に 1 群足す。**`face_srs.rs` の余地は 102 行**なので、この便はそこへ 15 行程度しか置けない。収まらなければ面へ出すのを G7b（file を割る）の後に回す。
- **生成区間は自動で追随する。** `schema.rs` の `TARGETS` は既に `srs.yaml`（`check::SRS_FLOOR`）を持つので **`schema.rs` は 1 行も触らない**。要件書 FR19 の対象も増えない。版上げは生成区間の再生成と 14 対の書き写しぶんだけ。
- 歯は `crates/folio/tests/check.rs`（862）と `tests/schema.rs`（624・生成区間の写しの期待値）、凍結 anchor は `tests/fixtures/schema/` の要件書の区間 1 本。

**なぜ `basis` を広げないか。** 要件書の `basis` に条以外の id を書くと、`face_srs.rs` の 1028〜1030 行が `ctx.article(&q)` で条として解こうとして落ち、歯 29 本が赤になる（1 回目の後付けの実測）。制約の行も同じ関数（1148 行）を通る。欄の意味は「条だけ」に閉じており、広げると面の契約が壊れる。

#### G0-a2 の中身（見立て・先に判断の記録が要る）

- **規則の表の行 → 条以外（33 対）。** `article` は単値で、`refs.rs` が行 R-4 の双方向の式の中で `as_str` で読む。一覧にするのも `basis` を id の欄に作り直すのも、**R-4 の値と母集団の定義に触る**。R-4 は凍結の行なので、動かすなら裁定が要る（条 P-17.1）。**便より先に判断の記録**で、本ノートの ADR-13 決定 (3-b) がそれを定める。
- **判断の記録 → 生んだ要件・規則（12 対）。** 1 回目の後付けはこれを `basis` に書いたが、面の章 04 の見出しは「**根拠**と撤退条件」（`face_adr.rs` の `CHAPTERS`）なので、公開される根拠の欄に帰結が混ざる。**帰結の欄を別に足し、`basis` には書かない。** 欄の決まり（`adr/schema.yaml` の `basis_note`）の側で決める話であって、書き手の一存ではない。
- **触る先**: `refs.rs`（双方向の式）・`rules.rs`（閉じた一覧）・`adr.rs`（帰結の欄）・`face_constitution.rs`（規則の表の面）・生成区間・凍結 anchor・歯が同時に動く。**M（300 行程度）**。
- **33 対の効き目は薄いかもしれない。** 多くは「この行の判定は『まだ分からない』（P-4.2）」の類の言い換えの参照で、辺に昇格しても近傍はさほど太らない見込みである。**G0-a1 の効き目を測ってから G0-a2 の大きさを決める。**
- **要件書の項 → ほかの要件・制約（12 対）は保留する。** 意味が一定でない（「撤去の前提」「構造の床に寄せた」「制約から要件へ」）ので、1 つの欄に混ぜると後で何の辺か機械で言えなくなる。G0-a1 の後の数えを見てから決める。

## 9. 退ける案

### 9.1 影響集合で束を切る（v2 の形）

**退ける。目的が精度だから。** 束を切ると、切った先に在る食い違いを観点は見られない。辺を昇格させた後でも「止める」の 6 件が 2 段の外に在る（§1.7）。v2 はこれを「撤退条件で数える」で受けようとしたが、**数えられるのは見つかった後であって、見つからなかったものは数えられない。**

字数では v2 の形が勝つ（1 周 22% 対 42%）。**その差は精度で払う値段としては高すぎる**、というのが裁定の読みである。

### 9.2 根本から作り直す（持ち主の第 2 の選択肢）

**部分的に採る。** 持ち主の言葉は「リンクとノードの対応をしっかり作り込む方向で設計を根本から考え直すか」だった。v2 はこれを「id の体系ごと作り直す」と読んで、退ける実証を示そうとして失敗した。

**v3 は「リンクとノードの対応を作り込む」の部分を採る**（散文の言及 258 対を型付きの欄へ書き写す・床の規則で維持する）。実測で 4 観点すべての精度が上がる（§1.7）。

**採らないのは「id の体系ごと作り直す」の部分**である。作り直せば 12 本の判断の記録と 27 条と 20 要件の id の連続性（P-7.1 が禁じる改番）と 3 本の凍結 anchor を失う。後付けはそれを 1 つも失わずに同じ利益を取る。

### 9.3 散文の言及を走査で拾って辺として使う（書き写さずに）

**退ける。** 走査で救い上げる形は、①「本当の依存」と「履歴・説明」を機械が区別できない ② 条 N-2 の向きに反する（散文にしか無い関係を機械の判定の根拠に昇格させる）③ 走査の式が変われば辺が変わる。**書き写せば、依存は型付きの欄に在り、床が数え、人が読める。**

### 9.4 文書ごとの印（`ceiling-gate.md` §4 案 B）

**節点の単位に置き換える。** 案 B は「× 整合の観点は差分にできないので費用は半分にしかならない」と自分で書いていた。実測でもそのとおりで、整合 は読む欄まで絞っても 59.6% を読む。v3 では印の単位は「周を回すか」と「門が何を止めるか」にだけ効き、束の大きさには効かない。

### 9.5 注意の先を 1 段にする／3 段にする

**2 段を採る。** 1 段では 整合 の所見の 2 段以内の割合が大きく落ち、3 段では近傍が辺を持つ節点のほぼ全部に届いて一覧が一覧でなくなる。**束を切らないので、この選択は精度ではなく一覧の読みやすさの問題である。**

### 9.6 4 観点に別々の半径を与える

**与えない。** v2 は 整合 だけ 2 段、ほかを 0 段としていた。それは束を切る設計での費用の妥協だった。**束を切らない v3 では 4 観点とも同じ 2 段でよい**（一覧の字数は 4 観点合わせても束の 1% 未満）。§1.7 の実測で、3 観点も 2 段以内に 83.8〜85.3% の所見が入る。

### 9.7 持ち越しを入れる

**退ける。** 所見の 27.6%（「止める」3 件を含む）を失う（§3.5）。束を切らない v3 では、持ち越しが無くても 1 周の字数は変わらない。

### 9.8 グラフを人が書く file に持つ

**退ける。** P-6.4。索引は導出物だけにする。

### 9.9 床を「憲法だけ」にする

**退ける。** 語彙の語と天井の観点に置かれた所見（整合だけで 29 件）は型付きの辺を持たず、伝播では届かない。語彙と規則の表は入口の棚で憲法の付録（`shelf.annexes` の `inside: constitution`）と定められている。**v3 は束を切らないので、そもそも床の外を落とさない。** 床の一覧は「注意の先の外でも必ず読ませる」ものの定義としてだけ残る。

## 10. 撤退条件と、持ち主が裁定した 4 点

### 10.1 撤退条件（P-8.1・数えるのは orchestrator 席・記帳は台帳 f2-648）

1. **注意の先が当たらない**: 「止める」の所見のうち、**注意の先の一覧（変わった節点・2 段の近傍・参考）に 1 つも挙がっていなかった節点**に置かれたものを数える。**5 件で注意の先の一覧を捨て、束だけを渡す形に戻す**（束は元から切っていないので、捨てても見える範囲は減らない）。v2 の撤退条件 1 は「影響集合の外の所見が出たら判断を捨てる」だったが、v3 は束を切らないので**捨てるのではなく測る**形に変えた。
2. **辺の型が足りない**: 上の 1 で数えた所見のうち、**後付けの後も型付きの辺で 3 段以上離れていた**ものを数える。**3 件で、辺の型を足すか設計を根本から見直す設計ノートを起こす。**
3. **辺の追加が周を呼ぶ**: §3.4 の「辺の追加は引き金に数えない」を入れた後に、辺だけが変わった変更に由来する「止める」の所見が出たら数える。**2 件で辺の追加も引き金に数える形へ戻す**（持ち主の裁定「天井を高い頻度で走らせる種になるなら微妙」の測り方）。
4. **索引が実時間を取り戻さない**: 索引を組む口（G1）と注意の先を組む口（G5）の所要の合計が、1 周の所要（15〜20 分）の 1 割を超えたら数える。**実測 3 回で G5 を止める**（索引と全体像の出力は残す）。
5. **門を緩めた対価**: 門が「まだ分からない」を出さずに通した便のうち、**着地の時点で印に不合格の節点が残っていた便の本数**を数える。**2 本で §4.2 の緩めを捨て、判定を repo 全体へ戻す。** 単位を周ではなく便の本数にしたのは、周が起きない失敗の形を数えるためである。
6. **周の引き金が漏れる**: §3.4 の引き金で「周は要らない」と出した後に、次の周でその変更に由来する「止める」の所見が出たら数える。**2 件で引き金の判定をやめ、設計文書の file が 1 つでも変われば周を回す形に戻す。**
7. **数えられない回**が規則の表の行 R-7 の回数を超えたら、本判断の撤退条件の判定を「まだ分からない」に落として持ち主へ渡す（条 P-4.2・P-11.1）。

### 10.2 持ち主が裁定した 4 点（2026-09-22 11:42 JST「全部承認する」・推奨どおり）

4 点とも推奨どおりに確定した。承認は 3 つを 1 つにまとめた要求への回答で、一括 11 と辺の後付け（PR #240）と本判断の発効を同時に通している。以下は経緯として残す。

**1. 持ち越しを入れるか。**（v2 の 2 点目）
天井は AI の判定で、束が 1 byte も違わない 2 周を突き合わせたところ、判定（合格）は一致しましたが、挙がった所見 7 種のうち両方で挙がったのは 1 種だけでした。過去 23 周に持ち越しの条件を当てると、所見の 27.6%（「止める」3 件を含む）が消えます。
**推奨は「入れない」。** 束を切らない形にしたので、持ち越しが無くても 1 周の字数は変わりません。効く軸は精度だけで、そこでは純粋な損です。
→ **確定: 持ち越しは入れない。毎周、観点に問い直す**（ADR-13 決定 (7)）。

**2. 門をどこまで緩めるか。**（v2 の 3 点目）

**3. 判断の記録 ADR-8 の決定 (4) を狭めることを、どう記帳するか。**（v2 の 4 点目）

### 10.3 まだ確かめていないこと

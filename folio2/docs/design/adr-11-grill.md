## 発効を止める重さ（G-n）

### G-1. P-5.6 が掛かる「範囲」の正本が散文にしかない ＝ F-1 の構図の再生産

**場所**: 憲法 `constitution.yaml:187`（P-5.6）／ADR-11 `decision` (2)／語彙 `vocabulary.yaml` typed-data。

**逐語**:
- 条 P-5.6「実装の型付きの定数を規則の正本とするとき、その写しを人が読める型付きデータとして設計文書の置き場へ決定的に導出する。」（限定語なし）
- 条 P-5.1「規則・閾値・型の一覧は型付きデータ（正本 YAML・rules 行・部品目録・実装の型付きの定数）に置く。」（限定語なし）
- 語彙「実装の型付きの定数 = 道具の中に型を付けて書いた**値の一覧**（欄の集合・値域・閉じた一覧）」
- ADR-11 決定 (2)「P-5.6 が言う「規則の正本とする定数」の範囲 = **床・天井の所見の検査・散文の門**が、違反か「まだ分からない」を出す判定に使う 欄の集合・値域・閉じた一覧。file や置き場の名、画面と文言の字面、体裁の幅のような生成器の内側の値、面の生成器が値に名札と見た目を当てる表は、規則の正本ではなく範囲の外とする。」

**なぜ**:

1. 外延が 3 つある。条（無限定）⊃ 語彙（「値の一覧」＝単一の値は外れる）⊃ 決定 (2)（執行者を 3 つに絞る）。どれが規則かを条も語彙も決めていない。
2. **注入される面には最も広い読みしか載らない。** 実測: `folio inject --print` の本文 7,845 byte は規範文と前文だけで（rules 行 R-2 の projection「前文（順位）+ 各条の規範文（id と本文）だけを注入する」）、語彙も判断の記録も入らない。CLAUDE.md を読む AI は、P-5.1 の括弧を「実装の定数はどれでも型付きデータ」と読み、P-5.6 を「実装の定数はどれでも写しが要る」と読む。除外を知る手立てが無い。
3. これは F-1 が止めた構図そのものである。反証 F-1 の逐語:「本件は機械が執行する規則の正本を条が名指さない面（実装の code）へ置き、その許しを**判断の記録の本文**が与えている」。ADR-11 は条の側を埋めた代わりに、「どの定数が条の対象か」を判断の記録の本文に置いた。2 周目の整合の審査役は同じ形を同じ基準で拾える。
4. N-2.1「変更が、散文・記憶・会話にしか無い規則を持ち込むなら、それを規則として扱わない。」に触れうる。決定 (2) は「範囲の外とする」という**規則**であり、置き場は判断の記録の散文である。

**直し方**（どれか 1 つ）:
- (a) 語彙の「型付きデータ」の定義に、含む側だけでなく**外す側**も書く（今は含む側しか書いていない）。1 文で済み、条文は動かない。
- (b) rules の discipline 節に D 行を 1 本足し、範囲（含む・外す）を型付きの値として持つ（P-17 の裁定 id が付く＝変更に門が掛かる）。G-6 の一部も同時に塞げる。推奨。
- (c) P-5.6 の条文に範囲を書く。数値を書かない決まり（schema.statement.numbers）には触れないが、1 文に収まらない見込みで one_sentence と衝突する。採らない。

### G-2. 決定 (2) の範囲の定義が、決定 (3)(4) の対象の半分を外す（自家撞着）

**場所**: ADR-11 `decision` (2) と (3)(ウ)・(4)③④ の突き合わせ。

**実測**（下調べ `docs/design/adr-11-survey.md` §6 と src）:

| 一致を確かめている口 | 本数 | 決定 (2) の「床・天井の所見の検査・散文の門」に入るか |
|---|---|---|
| 床（`folio check`） | 11（A1〜A11） | 入る |
| 面の生成器（`folio face`） | 5（A12〜A16） | **入らない** |
| 命令（`folio ceiling` の束） | 2（A17・A18） | 境界（束を組むのは検査ではない） |
| 歯（`cargo test`）だけ | 4（A19〜A22・部品目録） | **入らない** |

ところが同じ判断の記録は、

- (3)(ウ)「中身を人が書く行の id の集合を実装が固定する形（**天井の観点 4 つと読む文書・入口の棚**）は…」→ 入口の棚 = A12〜A15 = 面の生成器。
- (4)③「**部品目録**の上限 3 本と図の型の名札 1 本＝組み立て時の導出に足す」→ A19〜A22 = 歯だけ。
- (4)④「**入口の棚**の閉じた id の集合＝生成区間へ」→ 同上。

と、(2) が範囲の外に置いたものを便に起こす。さらに (2) は「面の生成器が値に名札と見た目を当てる表は…範囲の外とする」と書きながら、(3)(ア) の後半でその表の扱い（片方向の引きに留める）をわざわざ決めている。範囲の外なら決める必要が無い。

**なぜ重いか**: 便を受ける側が「(2) の範囲」と「(4) の割り」のどちらに従うかを黙って選ぶことになる。ADR-9 の grill G-3（導出の範囲が未決なので便を受ける側が黙って選ぶ）と同じ型の欠けである。

**直し方**: (2) の執行者の列挙を「folio が違反か『まだ分からない』を出す全ての口（床・面の生成器・命令・歯）」に直す（推奨。(3)(4) がそのまま通る）。または (3)(ウ)・(4)③④ を範囲の外の「任意の片付け」と明記して、P-5.6 の義務ではないと書く。

### G-3. 条の型（pattern: event）と帰結（未達が残る）が両立せず、機構の宣言が実測より広い

**場所**: 憲法 `constitution.yaml:187`（`pattern: event`）・`:193`（P-5 の mechanism）／ADR-11 `consequences` 2 つ目。

**逐語**:
- 帰結「発効した時点で、決定 (2) の範囲に入るのに写しが無い定数（下調べの ③）と、向きが決まっていない二重の記述（① と ②）は、条と決定に対して**未達のまま残る**。」
- 憲法 P-5 mechanism（改訂案）「…実装の型付きの定数の写し（生成区間）は folio schema --check が導出との byte 一致を数える（P-5.6・FR19）。」／`kind: build-check, live: now, polarity: fail-closed` は据え置き。

**なぜ**:

1. **event は 1 回の引き金の型**（面の名札 = 「〜のとき」・`face.rs:514` PATTERN）。発効より前に正本になっている定数は引き金を過ぎているので、event の読みでは「未達」ですらない＝下調べ ③（`docs/design/adr-11-survey.md` 類 B 51 本）は永久に義務の外に落ちる。帰結が言う「未達のまま残る」は、継続の義務（pattern: `state` か `ubiquitous`）を前提にした文である。条と判断の記録が別の義務を述べている。
2. **宣言した機構が、P-5.6 の違反の主要な形を数えられない。** 実測: `folio schema --check` の対象は `crates/folio/src/schema.rs:29` の `TARGETS` = `adr/schema.yaml` と `design-note/schema.yaml` の 2 file だけ（実行結果も「一致（adr/schema.yaml・22182 byte）」「一致（design-note/schema.yaml・14618 byte）」の 2 行のみ）。この検査が数えるのは「**既に在る写しが古くなっていないか**」であり、「**写しが 1 つも無い**」は 1 件も検出しない。P-5.6 が禁じる主要な状態に対して黙る。
3. その結果、`polarity: fail-closed` と `live: now` の宣言は過大になる。P-4.1「検査・生成が実行できなかった結果を「異常なし」として扱わない。」・P-4.2「判定できないものは「まだ分からない」として表に出す。」に照らすと、未達は今のところ違反にも「まだ分からない」にもならず、黙って通る。憲法 `schema.mechanism_live_rule`「kind が reject / build-check でも live が now でない条は、その検査結果を「まだ分からない」として出す（P-4.2）」の趣旨にも反する。

**直し方**:
- pattern を決める。継続の義務にするなら `state`（〜のあいだ）へ。新規の定数にだけ掛けるなら `event` のまま残し、帰結の「未達のまま残る」を「既に在る定数は本条の引き金の外なので、決定 (4) の便で自主的に揃える」に書き換える（推奨は前者＝ `state`。後者だと 51 本に条の後ろ盾が無くなり、案 c を退けた理由が自分に返る）。
- P-5 の mechanism を P-5.6 について分ける、または note に「写しの有無そのものを数える口は無い（live: M2）」と明記する。1 文で済む。

### G-4. 決定 (3)(ウ)(4)①④ は、持ち主が承認した一覧の正本を実装へ寄せる（P-5.5 前半・ADR-9 案 e の却下理由）

**場所**: ADR-11 `decision` (3)(ウ)・(イ)・(4)①④。

**実測**（実装自身が正本を名指している）:
- `crates/folio/src/ceiling.rs:30` `/// 観点ごとの 3 値（**要件書 FR5** の 3 値・順も固定）。`
- `crates/folio/src/ceiling.rs:33` `/// 観点の id の列（**ADR-8 決定 (1)**・順も固定・増減はどちらも違反）。`
- `ceiling.yaml` は持ち主の承認欄を持つ（ADR-10 決定 (2)④「発効のときに先頭の欄（meta）の承認の一覧へ 承認 の行（逐語・日付・版 v0.2）を足し」）。`index.yaml` の棚も持ち主の walk 承認済み。

**逐語**（ADR-9 案 e の却下理由・発効済み）:「file 全体を生成物にすると裁定の記録（meta.type_enum_ruling の裁定 id と逐語）と対応表（mapping）の正本まで実装へ移り、**P-5.5（原則と裁定の正本は設計文書）に反する**。」

**なぜ**: ADR-11 が P-5.5 の文を変えないと決めた以上、P-5.5 の前半（原則と裁定の正本は設計文書）は改訂後も生きる。観点 4 つ・読む文書 9 つ・棚の 4 行は、持ち主の承認を経た**裁定**である。(イ)「閉じた id の集合…は実装の型付きの定数が正本」＋(ウ)「閉じた id の集合は (イ) のとおり生成区間に出す」は、その裁定の正本を実装へ移す読みになる。しかも ADR-8 / 要件書 FR5 と実装の定数の一致を数える口は無いので、**黙って古くなる面が 1 つ増える**（本判断が是正しようとしている当のもの）。P-5.1 の括弧を広げたことで「2 面」は保たれるが、前半は保たれない。

なお (3)(ウ) の読み自体（規則と実体であって P-6.4 の二重の記述ではない）は、ADR-9 案 c と同じ言い逃れではない（→ S-8）。問題は読みではなく、正本を誰が持つかを書いていないことである。

**直し方**: (3) に 5 つ目の決まりを足す。字面の案:

> (オ) 持ち主の承認を経た一覧（天井の観点と読む文書・入口の棚・3 値）の裁定の正本は、その承認を持つ設計文書（判断の記録 ADR-8・要件書 FR5・各 file の承認欄）に留まる。実装の型付きの定数はその写しであり、生成区間へ出すのは実装からの導出ではなく「裁定 → 実装 → 生成区間」の 2 段であることを明記する。2 段の 1 段目（裁定と実装の一致）を数える口は無いので、その判定は「まだ分からない」として扱う（P-4.2）。

### G-5. 語彙「生成区間」の改訂が、改訂していない規範文 P-14.3 をその場で偽にする

**場所**: `vocabulary.yaml` generated-block の改訂案／憲法 `constitution.yaml:305`（P-14.3）。

**逐語**:
- 改訂後の語彙「生成区間 = **file の中で**、機械が書き換える印のついた範囲（**CLAUDE.md の憲法の写し・欄の決まりの file の決まりの部分**）。手で直さない（P-6.2・P-14）。」（改訂前は「CLAUDE.md の中で、機械が書き換える印のついた範囲」）
- 改訂しない条 P-14.3「**生成区間**の総バイト数は rules 行 R-2 以下に収める。」（限定語なし）

**実測**: `folio schema --check` = 「一致（adr/schema.yaml・**22182 byte**）」「一致（design-note/schema.yaml・**14618 byte**）」。R-2 の上限は「8,000 byte 以下」。

**なぜ**: 語の外延が広がった瞬間、P-14.3 は字義として破れる。機械は落ちない（rules 行 R-2 の what が「**CLAUDE.md 生成区間**の本文の総バイト数」と限定しているため）ので、**条文だけが黙って偽になる**。A-2.2「条文（…）が 1 文字も変わらない変更を改訂として扱わない」ゆえ、A-2 / N-4 の差分検査も拾わない。しかも **CLAUDE.md へ注入されるのは規範文だけで条の見出しは載らない**（実測: CLAUDE.md の生成区間は `P-14.3: 生成区間の総バイト数は…` の 1 行）ので、注入された面を読む AI には P-14 の見出し（「憲法を AI の手元へ写す（注入）」）による範囲の絞りが届かない。本判断は「人が書く面・古くなる面を減らす」ことを掲げながら、その第一歩で偽の規範文を 1 本作ることになる。

**直し方**: 同じ版の amends に 1 件足して P-14.3 の text を「**CLAUDE.md の**生成区間の総バイト数は rules 行 R-2 以下に収める。」に改める。費用は実測で足りる——改訂後の注入本文は 7,845 byte（`folio inject --print` 実測）で上限 8,000 byte まで 155 byte 残り、「CLAUDE.md の」は 27 byte。あるいは (b) 語彙を広げず、欄の決まりの file の側を別語にする。(a) を推す。

### G-6. 改訂の最大の対価——実装は規則の置き場の中でいちばん門が弱い——が判断の記録に無い

**場所**: ADR-11 `options` b.reason／`decision` 全体／`consequences`。

**逐語**（案 b の却下理由）:「**設計文書の置き場は便の門（契約の審査・実装の検査）を通らずに直せるので、形の決まりを緩める変更が便を通らなくなる。**」

**なぜ**: この文は片側しか見ていない。改訂後、機械が執行する規則の正本を置ける面は 3 つになり、変更の門は次のようにそろわない。

| 置き場 | 変更に要るもの | 機械の門 |
|---|---|---|
| 憲法 | 判断の記録 + 撤退条件 + grill + 持ち主の承認の逐語（A-2.1・N-4.1） | 凍結 anchor の差分の消し込み（実測: `design-intent/anchors/` に constitution-*.yaml が在る） |
| rules 行 | 裁定 id と時刻（P-17.1）・deny 行を緩めるなら A-2.3 の前置（P-17.4） | **今は無い**（P-17 の mechanism は `live: delivery-0`・`note: …CI は便 0 以降・それまでは PR の diff を人が見る`。rules の凍結 anchor も無い） |
| **実装の型付きの定数**（本改訂で追加） | **何も要らない**（便は前もって承認済みの運用。持ち主に問うのは 消す・憲法改訂・契約表外の依存 だけ） | 写しを持つ定数だけ、生成区間の差分が design-intent の PR に出る |

すなわち本改訂は「規則の正本の置き場を 1 つ増やす」だけでなく、「**持ち主の裁定を経ずに規則を変えられる置き場を、条の上で適法にする**」。P-5.6 が義務にするのは写しの**存在**だけで、変更の門については何も言わない。唯一の歯止めは「写しの差分が PR に出る」ことで、これは案 b の却下理由が設計文書の側について「門が無い」と断じたのと同じ水準（人が diff を読む）である。同じ基準を両側に当てていない。

A-2.3 が敵対的検証に求めるのは、まさにこの「主張する利益（実装に正本を置ける）の対価」の提示である。判断の記録に 1 行も無いまま承認を問うのは、持ち主に費用を伏せて便益だけを示すことになる。

**直し方**: 費用のほうを 2 文で書く。字面の案:

> 帰結: 本改訂は、機械が執行する規則の正本を置ける面のうち、変更に持ち主の裁定も裁定 id も要らない面（実装の型付きの定数）を条の上で適法にする。歯止めは、P-5.6 が要求する写しの差分が設計文書の置き場の取り込みの審査（PR）に必ず現れることだけであり、憲法（A-2）や rules 行（P-17）のような前置の門は掛からない。規則の正本とする定数を足す・値を変える便は、契約表の行にその旨を書き、取り込みの審査で生成区間の差分を必ず読む。

あわせて案 b の reason に「案 a も、実装の側は便で持ち主の裁定なしに変えられるという逆向きの弱さを持つ」を 1 文足す（比較の公平・ADR の hallmark）。

## 直すとよい（D-n）

### D-1. (3)(ア)「面の生成器の名札の表は写しではない」は、鍵の列については事実でない

**実測**: 憲法 `constitution.yaml:37-46` の `schema.enums` 10 本に対し、`crates/folio/src/face.rs` は `TIERS`(461) / `STRENGTH`(509) / `PATTERN`(514) / `BINDS`(521) / `MECH_KIND`(522) / `LIVE`(528) / `STAGE`(535) / `POLARITY`(536) / `RATIONALE_KIND`(537) / `RETREAT_KIND`(542) の 10 表を持ち、**鍵の列の集合と順は値域と逐語で同じ**。新しいのは名札と class の列だけである。「値から見た目への対応であって写しではない」は、名札の列についてだけ正しい。

**さらに**: `crates/folio/src/check.rs` は `"enums"` を 1 度も読まない（grep 実測 0 件）。`schema.enums` を読むのは `link.rs:104`（retreat_kind）と `face_constitution.rs:154`（tier）の 2 本だけ。**8 本の値域は誰も読まない**＝憲法に書いた値域は実質 飾りで、実効の値域は `face.rs` の表にある。

**片方向に留めると黙って古くなるもの**:
1. 値域を**狭める**改訂（A-2 の承認つき）が面に届かない。憲法が許さなくなった値を面が描き続け、何も落ちない。
2. 値域を**広げる**改訂は、実例がその値を使うまで面が気づかない。
3. 順と字面の食い違いは既に発生している。実測（下調べ §5）: `rules.yaml:17` `status: [仮, 凍結, 未定]` vs `face.rs:552` `RULE_STATUS` = `[凍結, 仮, 未定]`。誰も落とさない。
4. `retreat_kind` は `face.rs:542` / `adr.rs:50` / `render.rs` の 3 枚あり、突き合わせを持つのは `adr.rs` の 1 枚だけ。

**直し方**: `face_constitution.rs:152-164`（tier の集合一致）を汎用の 1 関数にして 10 表に当てる。落ちたら違反ではなく「まだ分からない」（面が出ない）で足りるので床は増えず、N-5.1 にも触れない。(3)(ア) の 1 文を「表の鍵の列は値域の写しなので集合一致を面が数える。名札と見た目の列だけが表の持ち物」に直す。

### D-2. (3)(ア) の理由「A-2 と P-17 が変更を見張る」は rules.yaml の schema 節には当たらない

**逐語**: P-17.1「**rules 表（R-n・D-n）の行**の追加・変更は、裁定 id と時刻を行に付ける。」＝行だけ。A-2.1「**条文**を改訂するとき」＋ `constitution.yaml:28` `amendment_scope: [schema, precedence, articles]`＝憲法だけ。

**実測**: `rules.yaml` の `schema.enums` / `schema.top_level` を見張る口は無い。`check.rs:220-232` の `schema_top_level` は**その file 自身の** `schema.top_level` を読んでその file の節を数える＝自己参照で、節を足したければ `top_level` に足せば通る。`ceiling.yaml` / `index.yaml` / `intake.yaml` / `parts.json` にも A-2 / P-17 の門は無い。

**なぜ重要か**: (ア) が「持ち主か設計文書が決める値」を file 側の正本にする根拠として挙げた門が、(ア) が列挙する対象（規則の表の値域・部品目録・相談窓口の回答の値）の大半には掛かっていない。G-6 の「門の比較」を書くときに同じ事実が要る。

**直し方**: (ア) の括弧の理由を「A-2 と P-17 が見張る（憲法の値域のみ）／それ以外は取り込みの審査で人が読む」と正直に書き分ける。

### D-3. 撤退条件 (b) の「1 件」の数え方が無い（ADR-9 で一度直した欠けの再発）

ADR-9 の撤退条件は「（**器の断りの記録 1 回を 1 件と数える**）」と明記した（grill D-2 の反映）。ADR-11 の (b)「決定 (4) の便が便の上限に収まらず割り直しになった回数」には数え方が無い。「上限」が何か（契約表の行数か src の余地か）も書いていない。**直し方**: 「受付の断りの記録 1 回を 1 件」「1 本の便を 2 本以上に割り直した記帳 1 回を 1 件」のどちらかを本文に書く。

### D-4. 撤退条件の始点「①〜③ の便が着地した後の周」が、いちばん起こりやすい失敗を数えない

**逐語**:「決定 (4) の ①〜③ の便が着地した後の周でどちらかが R-7 の上限を超えたら…」

**なぜ**: (b) が数えるのは便の割り直しである。①〜③ が割り直しを繰り返して**着地しない**とき、判定の日が来ない＝条件が発動しない。つまり「案 a の便が大きすぎて運べない」という、案 b へ移るべき最大の理由が、撤退条件の設計上いちばん検出されにくい。ADR-9・ADR-10 の撤退条件には始点の門が無く、ADR-11 だけが足している。

**直し方**: 「ただし ①〜③ のいずれかの便で (b) が R-7 の上限を超えたときは、着地を待たずにその時点で判定する」を足す。始点の門そのものは（①〜③ の着地で所見が消えるかを見るという趣旨は正しいので）残してよい。

### D-5. 決定 (3)(エ) の後ろ盾（P-17）は今 live でない

**逐語**: 憲法 `constitution.yaml:356` P-17 の mechanism `{kind: reject, live: delivery-0, stage: post, polarity: fail-closed, note: rules 行の diff に裁定 id と時刻が無ければ落とす（CI は便 0 以降・それまでは PR の diff を人が見る）}`。憲法 `schema.mechanism_live_rule`「kind が reject / build-check でも live が now でない条は、その検査結果を「まだ分からない」として出す（P-4.2）」。

**実測**: 凍結 anchor は憲法だけ（`design-intent/anchors/` = `constitution-v1.0.yaml`・`index.yaml`）＝rules 行が「変更されたか」を機械が測る基準が無い。R-16 の値のように実行時に読む行は、古い裁定 id を残したまま値だけ変えても落ちない。

**なぜ**: (3)(エ) の理由は「裁定 id と時刻を付ける仕組み（P-17）と、値を緩める前の検証（P-17.4）が規則の表の行にしか掛からないため」だが、今日その仕組みは人が PR を読む水準にある。決定の向きは変えなくてよい（実装よりは強い）が、帰結に事実として書く。

### D-6. (4)② 「正本が 2 つに読める箇所の解消」は実装の形と噛み合わない

**実測**: `crates/folio/src/adr.rs:97` は `pub(crate) const FLOOR: Floor`（コンパイル時の定数）で、`schema.rs:29` の `TARGETS` がその木から生成区間を書く。生成区間の印そのものが `schema.rs:22` で「**正本は実装の定数**（folio schema --write が書く）」と宣言している。一方 `link.rs:157` の違反の字面は「**憲法が正・床の定数を直す**」で、`adr/schema.yaml` の `enums_note` も「retreat_kind は憲法 schema.enums.retreat_kind と同じ（食い違えば落ちる）」と書く（＝ADR-11 の context が言う「正本が 2 つに読める」は実在する・S-5）。

**問題**: (4)② は「実装が file から読む形にし、撤退条件の種類の手書きの写しを無くす」と書くが、**実行時に読む値は `const FLOOR` に入れられない**。したがって
- (i) `retreat_kind` を生成区間から外す（＝ADR-9 / ADR-1 が決めた欄の決まりの file の内容が変わる）か、
- (ii) 生成区間の入力に憲法を足す（＝生成区間の先頭の宣言と要件書 FR19 / AC17 の受入基準が変わる）

のどちらかを選ぶ必要がある。判断の記録はどちらも書いていない。**直し方**: (4)② にどちらを採るかを 1 文で書き、要件書の版を足す帰結（既に在る）にその旨を含める。

### D-7. context の件数が実測と合わない（② の 2 本は二重計上）

**逐語**（ADR-11 context）:「② 同じ一覧が 2 か所に在るのに**誰も一致を確かめていない**もの **23 本**（憲法と規則の表の値域 13 本は面の生成器が名札の表として持つ・相談窓口の回答の値 2 本・実装の中どうしの写し 8 本）」

**実測**（下調べ §1′-1）:「`tier`（A16）と `retreat_kind`（A9・adr.rs 側）の **2 本だけ**が突き合わせを持ち、残り 8 本は片方向の `lookup` だけ」。すなわち 13 本のうち 2 本は確かめており、かつその 2 本は ① の 22 本（A9・A16）にも数えられている。**② は 21 本**が正しい。

あわせて「実装の中どうしの写し 8 本」も、8 本のうち 3 本は実装の中どうしではない（下調べ §1′-2: `bundle.rs FACE_NAMES` ↔ `ceiling.yaml documents[].id` / `figure.rs QUALITY` ↔ `rules.yaml R-14` / `figure.rs FIGURE_TYPES` ↔ `parts.json`）。

さらに **③ には件数が無い**（下調べの類 B = **51 本**）。帰結 2 つ目「未達のまま残る」の重さが本文から読めない。件数を書く。

### D-8. 基準（basis）に、本文で使っていない id が 3 つ・本文で使っているのに無い id が 1 つ

**実測**（欄の値だけを数え、先頭の YAML の注は除く）: `P-8` = 0 回・`N-3` = 0 回・`N-4` = 0 回（N-4 は先頭の注に 1 回だけ）。逆に `P-13` は帰結で 1 回使う（「版付きで足す（P-13.3）」）が basis に無い。

ADR-9 の grill D-10 と同じ指摘である。特に **N-3 は外すのでなく本文で使うのが筋**——(3)(ア) が値域を file 側の正本に戻すことで data 側に規則を緩める口が生まれないか（ADR-9 案 d を退けた理由）は、本判断が答えるべき論点であり、今どこにも書かれていない（相談窓口の回答の値がその典型・→ D-9）。

### D-9. (3)(ア) が「相談窓口の回答の値」を file 正本にする根拠が無い（ADR-9 案 d との線引き）

**逐語**（ADR-9 案 d の却下理由）:「data 側が規則を緩める口そのものになる（承認者・対話面・裁定 id の形・案の最小数を書き換えれば検査が緩む）。…N-3.1（例外機構を足さない）に正面から反する。」

ADR-11 (ア) は「相談窓口の回答の値」を file 正本（実装が読む）に置く。`intake.yaml answers.values` は既に実装が読んでいる（`intake.rs:46-58`・下調べ 類 C）が、`sheet.rs:28-29` の `YES` / `NO` を YAML から読む形にすると、回答の字面が data 側で動く＝支度表の判定が data 側から変わる。(イ) の線引き（「検査される file の側から緩められてはならない形の決まり」）がこれを (ア) に入れる理由を、判断の記録は書いていない。**直し方**: (ア) に「回答の値は持ち主が文言を選ぶもので、値域が増えても床の判定は緩まない（行き先の解決は `targets[].id` が閉じる）」といった 1 文を足すか、(イ) へ移す。

### D-10. 判断の記録の平易文が、決定 (2) の除外を落として義務を広く見せる

**逐語**: plain「**道具の中にしか無くて誰も読めない決まりは認めません。**」／決定 (2)「file や置き場の名、画面と文言の字面、体裁の幅のような生成器の内側の値、面の生成器が値に名札と見た目を当てる表は、規則の正本ではなく範囲の外とする。」

範囲の外にした値は「道具の中にしか無くて誰も読めない」まま残る（実測: 下調べ 類 B 51 本）。天井の 2 周目は、まさに「平易文が規範の字面とずれる」形（ADR-10 の「半分以上」・要件書 AC10 の「数値」）を止める所見にしている。同じ観点が本文にも当たる。**直し方**: 1 文足す——「ただし、機械が決まりとして使う一覧だけが対象で、ファイル名や画面の言葉づかいは含みません。」

### D-11. 憲法の平易文の追記に、非エンジニアに通らない語が 1 つ残る

**逐語**（憲法 `constitution.yaml:188` の追記）:「道具の中に型を付けて書いた決まり（**実装の定数**）も表の 1 つに数えますが…」

同じ判断の記録の平易文は「プログラムの中に型を付けて書いた値」と言い換えている。括弧の中の「実装の定数」は裸の専門語で、R-10 の機械（有無だけ数える）は拾わないが天井の領分である。**直し方**: 括弧を落とすか「（道具の作り手が書く値の表）」に置き換える。

### D-12. 帰結 1 つ目の「版に依らない形へ直す便を先に運ぶ」は、既に済んでいる

**逐語**（帰結）:「実の憲法の版と anchor の本数を字面で固定している歯（版の凍結の歯ほか）は、改訂の前に版に依らない形へ直す便を先に運ぶ。」

**実測**: 版の凍結の歯 `crates/folio/tests/freeze.rs` は冒頭の注のとおり「tests/fixtures/floor_base/design-intent/（憲法 v1.0）」の写しで回り、実の憲法を読まない（`bump_title` が探す `"\n  version: v1.0\n"` は fixture の側）。実の repo を読む `tests/anchor.rs:115` は**列の根**（`constitution-v1.0.yaml`）を読むので改訂で動かない。`tests/face_index.rs:722` の実の正本の歯は期待を正本から導く。便 43 / 44（f2-648.59 / .60）で済んだ作業である。**直し方**: 「済んだ（便 43 / 44）」と書くか落とす。残すなら、どの歯がまだ字面で固定しているかを名指す。

### D-13. 決定 (4) が、決定 (2) の範囲に入る対象を拾い落としている

**実測**（いずれも床が違反を出す判定に使う閉じた一覧＝(2) の範囲に当たるのに、(4) の ①〜⑦ のどれにも入らない）:

- `refs.rs:28` `SRS_ID_PREFIXES`（5・`prose.rs:30 REQUIREMENT` に写し）
- `refs.rs:25` `RELATION_NAMESPACES`（4）
- `refs.rs:22` / `link.rs:30` / `note.rs:742` / `prose.rs:13` の `RULE_SECTIONS`（2）× 4 枚

## 支持（S-n）

### S-1. 向き（条と語彙を直す）は F-1 の反証の支持の根拠にそのまま応える

反証 F-1 の支持の根拠 4 点（括弧の 3 つはいずれも版管理の中の型付き file・ADR-5 案 d と ADR-6 案 b が 2 度 code を外に置いた・ADR-9 自身が 2 度認めている・P-5.5 の「限る」）は、本審査でも正本に逐語で実在することを確かめた（`ADR-5.yaml:14`・`ADR-6.yaml:12`・`ADR-9.yaml` の案 a / 案 d の reason）。条の括弧を 3 → 4 にすれば根拠 1・4 は解け、根拠 2・3 は「以後は条が許す」で置き換わる。**正しい向きである。**

### S-2. amends 4 件は実測の差分と 1 対 1（余りも欠けも無い）

`folio check --emit-amends` の出力（実測）と ADR-11 の `amends` は、target / field / version / previous_text / new_text の全欄が字面まで一致する。4 件ちょうどで、余った差分も余った記録も無い。`statements.order` の差分が出ないこと（新設の id は「共通の id」に入らない）も実測で確かめた。

### S-3. P-5.6 の文面は憲法 schema 節の 5 つの決まりを満たす

`constitution.yaml:29-35` の `statement` に照らして実測:
- `one_sentence`（「。」1 つ）: ✓
- `one_polarity`（must ⇔ 文末が「〜ない。」以外）: 「導出する。」で ✓
- `numbers: forbidden`: 数字なし ✓
- `language: ja-first`（裸の英語キーワードを置かない）: ✓
- `pattern: event`（「〜とするとき、」）: 型としては ✓（ただし意味の当否は G-3）

### S-4. R-2（注入の上限）は守られる

実測: `folio inject --print` = 7,845 byte（現行の生成区間は 7,632 byte・P-5.6 の 1 行が 181 byte）。上限 8,000 byte 以下 ✓。`folio inject --check` は「区間 7632 byte ≠ 導出 7845 byte」で、発効後の再注入 1 手で揃う。

### S-5. 「撤退条件の種類の正本が 2 つに読める」という context の主張は実在する

実測で両側を確認した: `schema.rs:22` の生成区間の印「正本は実装の定数」／`link.rs:157` の違反の字面「憲法が正・床の定数を直す」／`adr/schema.yaml` の `enums_note`「retreat_kind は憲法 schema.enums.retreat_kind と同じ（食い違えば落ちる）」。同じ生成区間の中に 2 つの正本の宣言が同居している。本判断が拾うべき箇所という評価は正しい（ただし解き方は D-6）。

### S-6. 案 c・案 d の却下理由は正本の文から立つ

- 案 c（括弧に足すだけ）の却下理由「写しの無い定数（下調べの ③）まで条の上で適法になり、天井の審査役と持ち主が規則を読めない状態を条が追認する」は、下調べの類 B 51 本という実測に支えられている。
- 案 d（ADR-9 の 1 文を取り下げる）の却下理由「P-5.5 は…2 面に限っているので、正本が実装に在る事実と両立する説明にならない」は、反証 F-1 の支持の根拠 4 と同じ筋で正しい。

### S-7. P-5.5 の文を変えない判断は成り立つ（Q1 の本筋）

P-5.1 の括弧が 3 → 4 になれば、「型付きデータ」の外延が実装の定数を含み、P-5.5 の「この 2 面に限る」は文を変えずに保たれる。**語彙が CLAUDE.md に注入されないという弱点も、括弧の側に書いたことで消える**（注入される規範文だけを読んでも「実装の型付きの定数」が carrier だと分かる）。ここが案 a の設計上の強みで、語彙だけを直す案より優れている。裁定（P-5.5 も名指し）とのずれは note 欄で開示され、発効の承認で問うと書かれている（P-12 の作法として正しい）。ただし P-5.5 の**前半**が新しい制約になる点は書かれていない（→ G-4）。

### S-8. (3)(ウ) の読みは ADR-9 案 c と同じ言い逃れではない

ADR-9 案 c は「形を変えず、根拠だけ書き足して所見を退ける」ものであり、反証役は「schema.yaml を生成物と宣言した箇所が無い・生成の命令も無い」という**構造の不在**で潰した。(3)(ウ) は読みだけを足すのではなく「閉じた id の集合は (イ) のとおり生成区間に出す」という**構造の変更**を伴う。変更後は、id の集合は導出物・行の中身だけが人の手書きになり、床が数えるのは「規則が名指す id ごとに実体の行が 1 つある」という**外部キーの検査**になる。P-6.4 の 3 要素（2 面とも人が書く）は成立しない。反証 F-2 が `VIEWPOINT_IDS` / `DOCUMENT_IDS` を同じ形として数えたのは現状についての判定であり、(4)① の着地後は当たらなくなる。**読みは支持する**（残る問題は誰が正本かで、それが G-4）。

## まだ分からない（U-n）

### U-1. 決定 (4)① の便が 1 本に収まるか

`ceiling.rs` の 8 定数のうち 6 か所を生成区間へ出し、★2 本を「id の列だけ」の 2 段にし、`bundle.rs` の写し 2 枚を 1 枚に寄せ、天井の正本を第 3 版へ上げる——を 1 便で運べるかは、受付の時点の余地の実測に依る。本審査では測っていない（撤退条件 (b) が数える対象でもある）。

### U-2. (4)① で天井の正本が第 3 版になると、3 周目の束が 2 周目と比べられるか

ADR-10 決定 (1) の撤退条件 ① の数え（1 周目 + 2 周目の合計・1 度だけ）は済んでいるので直接の衝突は無い。ただし本判断の撤退条件 (a) が数える「発効後の天井の周」は、正本の版が変わった後の周である。版を跨いだ比較の扱いは書かれていない。

### U-3. 決定 (2) の範囲に入る定数の総数

(2) の範囲を機械が数える口は無く、下調べも「類 B 51 本」を範囲の内外に仕分けていない。発効時に未達がいくつ残るかは、範囲の定義が型付きデータになるまで（G-1 の直し）決まらない。P-4.2 に従い「まだ分からない」に置く。

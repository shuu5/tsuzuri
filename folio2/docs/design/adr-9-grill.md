## 問い 1: 決定は P-6.3 / P-6.4 / P-6.2 / P-5.1 / P-5.5 / N-3.1 と両立するか

### 支持（両立する側）

**P-6.3・P-6.4・P-6.2 は満たす。** P-6.3 は「同じ内容を 2 つの面が持つとき、一方を正本とし、他方は導出する。」、P-6.4 は「2 つの面を人が書き、一致を検査で強制する設計を採らない。」、P-6.2 は「生成物を手で直さない。」である。ADR-9 の決定は「床の定数（…）から folio が決定的に導出する生成物とする（P-6.3）。人は生成物を直さない（P-6.2）。」と書き、3 条の要素をそのまま当てている。F-1 が指した形（2 面が手書き・1 字の食い違いで落とす）は、片方が生成物になった時点で成立しなくなる。

**N-3.1 は保たれる。** N-3.1 は「変更が規則の例外機構（無効化の旗・「今回だけ」の口）を足すなら、それを拒む。」である。導出物の側を人が直しても byte 一致の検査が落とすので、data 側から値を緩める口は増えない。実測でもこの性質は現行と同じ向きで、`tests/floor_cases.yaml` の 15 case（`owner-knob`・`approver-knob`・`surface-knob`・`ruling-pattern-knob`・`effective-status-knob`・`options-min-knob`・`id-pattern-knob`・`anchor-dir-knob`・`first-version-knob`・`marker-knob`・`projection-shrunk`・`projection-widened`・`statement-fields-tampered`・`schema-extra-field`・`floor-type-knob`）が data 側の書き換えを落とすことを凍結している。導出後も「書き換え → 不合格」は変わらない（落ちる理由の字面だけが変わる。問い 4 の指摘 D-1 を見よ）。

**P-5.1 は満たせる。** P-5.1 は「規則・閾値・型の一覧は型付きデータ（正本 YAML・rules 行・部品目録）に置く。」で、「置く」であって「正本を置く」ではない。導出物の `adr/schema.yaml` は依然として型付きデータであり、一覧はそこに在り続ける。ADR-9 の決定が「人が読む写しは残る」（案 a の text）と書くとおり。

**この配置は持ち主の 1 つの承認の内側にある。** ADR-1 は決定で「欄の決まりの閾値・値域・置き場（…）は床（check_draft.py）の定数とし」と書き、憲法 v1.0 と同じ 2026-09-13 の裁定（逐語「すべて承認する」・f2-648.2 notes）で発効した。すなわち「規則の値が実装の定数に在る」形は、P-5.5 を持つ憲法と同時に承認されている。ADR-9 はその配置を新たに作るのではなく、重複していた手書きの面を外すだけである。

### 反証（両立しない・少なくとも書けていない側）

**P-5.5 の「2 面」に実装が入るかを、決定も案も書いていない。** P-5.5 は「原則と裁定の正本は設計文書、機械が執行する規則の正本は型付きデータとし、置き場をこの 2 面に限る。」である。ADR-9 は規則の正本を実装の定数（`adr.rs` / `note.rs` の `FLOOR`）に置くと宣言する。この定数が「型付きデータ」に当たるなら両立し、当たらないなら 3 つ目の面になって P-5.5 の「限る」に反する。語彙の項「型付きデータ」は「欄と値の型が決まった表（憲法の正本 YAML・rules 行・部品目録）。機械が読んで検査できる。」と定義し、括弧の中は folio2 が現に持つ 3 つの carrier の列挙である。`const FLOOR: Floor = Floor::Map(&[...])` は字義どおり「欄と値の型が決まった表」で、定義文には当たり、例示には無い。どちらの読みも成り立つ以上、判断の記録が読みを 1 つ選んで書かなければ、2 周目の整合の審査役が同じ問いを P-5.5 の側から立て直せる。これは「解釈が分岐するなら明示的に提示する（黙って選ばない）」に当たる。

**同じ難点を、退けた案 b の却下理由としては挙げている。** ADR-9 は案 b の reason に「人が読める欄の一覧が無くなり、P-5.1（型の一覧は型付きデータに置く）を実装の定数だけで満たす説明が要る」と書く。採用した案 a も、正本の層では同じ説明を要する（P-5.1 ではなく P-5.5 の側で）。片方にだけ難点を数え、採用案の同型の難点を書かないのは、比較の不公平として読める。これは 1 文で塞げる（下の「直し方」を見よ）。

### まだ分からない

- 「型付きデータ」に実装の型付き定数が入るかは、語彙の項を改訂するか判断の記録が読みを宣言するまで決まらない。本審査では決めない（P-4.2）。

### 直し方（両立させる書き方）

決定の末尾に 1 文を足す。字面の案:

> 実装の中の型付きの定数（`Floor` の木）は P-5.5 の「型付きデータ」の 1 つとして扱い、規則の正本の置き場は設計文書と型付きデータの 2 面のままとする。人が読む型付きデータの面（欄の決まりの file）は、その正本からの導出物として残す。

あわせて案 a の reason に「案 b と同じ P-5.1 / P-5.5 の説明を要するが、人が読む型付きデータの面を導出物として残すことで、一覧は型付きデータに在り続ける」を足す。

## 問い 2: 退けた案 b・c の却下理由は事実に基づくか。抜けている案は無いか

### 支持

**案 b の却下理由は事実に基づく。** 「人が読める欄の一覧が無くなり」は正しい。現行の `adr/schema.yaml` は 24,933 byte・`design-note/schema.yaml` は 20,800 byte で、大半が `*_note` の説明と `plain` の平易文であり、退役すれば非エンジニアが欄の一覧を引く面が消える。「案 a の撤退先として残す」も、撤退条件の行き先と整合している。

**案 c の結論（却下）は正しい。** 反証役の逐語は「schema.yaml を生成物と宣言した箇所は無く、生成の命令も無い（同じ束で ADR-2 の帰結は anchors/ を「生成物（手で直さない・P-6.2）」と明記し、生成の命令 check_draft.py --freeze-anchor / --emit-amends を名指す。この非対称が「schema.yaml は導出されていない」の裏取りになる）」であり、ADR-2 の帰結を読み直してこの非対称は実在する。根拠を書き足す道は塞がっている。

### 反証

**案 c の却下理由が、案 c の主張とは別の主張への反証を引いている。** ADR-9 の案 c は「ADR-1 に『実装の定数は人が書く面ではない』等の根拠を足し、所見を退ける」である。これに対し reason が引くのは「床は初日（day-1）の道具そのもので P-5 と P-14 の機構が名指す・…道具（tool）を縛る条の射程の内側」という、**適用範囲（binds = tool）で退ける読み**への反証であって、「実装の定数は人が書く面ではない」への反証ではない。後者への反証は同じ refute.yaml の中に別に在る（schema.yaml が生成物と宣言されていないこと・`floor_note` の「変えるときは床の script を直す（取り込みの審査で読む）」が手作業の同期を前提にしていること）。結論は変わらないが、引く逐語が噛み合っていない。

**逆向きの案（欄の決まりの file を正本にして実装が読む）が options に無い。** これは反証役自身が是正の向きとして先に挙げた 2 つのうちの 1 つである。逐語:

> 是正の向きは P-5.1「規則・閾値・型の一覧は型付きデータ（正本 YAML・rules 行・部品目録）に置く」とも揃う＝**値の正本を欄の決まり側に置いて床が読む**、または床の定数から schema.yaml を導出する。

ADR-9 は後者を採ったが、前者を案として立てずに落としている。しかも前者こそ P-5.1 の括弧が字義で名指す carrier であり、問い 1 の難点を持たない。退ける理由は強く、かつ短く書ける（N-3.1 と ADR-1 の敵対レビュー 3 周の実測）。書かないまま落とすと、「最も筋の良く見える対抗案をなぜ退けたか」が記録に残らない。

**もう 1 つ、粒度の案（file 全体か schema 節だけか）が立っていない。** 問い 4 の G-2 / G-3 が示すとおり、導出の範囲の違いは実装可能性を変える。憲法の生成区間（P-14・`<!-- constitution:begin -->` から `<!-- constitution:end -->`）という前例があるのだから、「schema 節だけを生成区間にする案」は案として比べるに値する。

### 直し方（足す案の字面）

```yaml
  - id: d
    name: 欄の決まりの file を正本にし、実装が起動時に読む
    text: 欄の決まりの file 2 本を正本とし、床の定数を持たず、folio が起動のたびに読んで閾値・値域・置き場に使う。
    verdict: rejected
    reason: P-5.1 の括弧が名指す carrier に正本を置ける唯一の向きだが、data 側が規則を緩める口そのものになる（承認者・対話面・裁定 id の形・案の最小数を書き換えれば検査が緩む）。ADR-1 の敵対レビュー 3 周（2026-09-12・f2-648.2 notes）はこれを実測で示し、凍結 fixture の 15 case（owner-knob ほか）がその実証を固定している。N-3.1（例外機構を足さない）に正面から反する。
  - id: e
    name: schema 節だけを生成区間にする
    text: 欄の決まりの file のうち schema 節だけを印で挟んだ生成区間とし、meta・mapping・plain・先頭の注は人が書くまま残す。
    verdict: adopted か rejected（決定の範囲に合わせる）
    reason: 憲法の生成区間（P-14）と同じ型で、裁定の記録（meta.type_enum_ruling）と対応表（mapping）を設計文書の側に残せる。file 全体を生成物にすると、それらの正本まで実装へ移る。
```

（案 e は、問い 4 の G-2 の直し方と同じものである。採否は起草者が決める。）

## 問い 3: 撤退条件は「捨てる条件」として数えられるか

### 支持

**誰が・何を・どこへ記帳するかは在る。** 逐語は「数えるのは planner 席で、台帳に記帳する。発効後、生成物の欄の決まりの file を人が直して folio check が落ちた回数、または導出の口の不一致で便の受付が止まった回数が、同じ種類の失敗として rules 行 R-7 の上限を超えたら、本判断を捨てて案 b（欄の決まりの file を正本から外す）へ移る判断の記録を起こす。」である。`kind: measure` の定義（欄の決まりの `retreat_kind_note.measure` =「数えた値（回数・件数・byte）が条件に達したら捨てる」）に合い、行き先（案 b）も明示され、ADR-1・ADR-2 の撤退条件と同じ書き方になっている。「いつ」に窓（何日以内）が無い点は R-7 自身にも ADR-1・ADR-2 にも無いので、先例に揃っている。

### 反証

**2 つの失敗を「同じ種類の失敗」と呼ぶが、R-7 の定義では別種である。** rules 行 R-7 の `same_failure` は「（検査の id・判定・対象の path）の 3 つ組が一致する失敗を「同じ種類」とする」である。ADR-9 が挙げる 2 つは、検査の id も対象の path も違う（片方は `folio check` の欄の決まりの検査と `adr/schema.yaml`、もう片方は器の受付で、folio の検査 id も path も持たない）。R-7 の値は「2 回」なので、別種として別々に数えれば、どちらも 3 回目で初めて超える。まとめて数えるのか別々に数えるのかで、判断を捨てる時点が変わる。ADR-2 はこの点を自分で解いており、逐語は「（2 つは R-7 の same_failure では別種なので、別々に数える）」である。ADR-9 は同じ先例を持ちながら逆の語を使っている。

**2 つ目の事象は folio の数える面に無い。** 「導出の口の不一致で便の受付が止まった回数」は器（scribe2）側の出来事で、R-7 の 3 つ組（検査の id・判定・対象の path）に写せない。planner 席が台帳で数えること自体は可能だが、R-7 を物差しに使うなら「何を 1 件と数えるか」を本文に書かないと測れない。

### 直し方

`retreat.condition` の該当部を次の形にする（ADR-2 の書き方に揃える）。

> …回数（(a) 生成物を人が直して `folio check` が落ちた回数、(b) 導出の口の不一致で便の受付が止まった回数）を、R-7 の same_failure では別種として別々に数え、どちらかが R-7 の上限を超えたら…

## 問い 4: 帰結に書いた便は実現可能か。抜けている影響は無いか

### 支持

**終了コードの 3 値は前例と実測どおり。** 決定は「無い 2・不一致 1・一致 0・folio inject と同じ型」と書く。`crates/folio/tests/inject.rs` は `inject_fixture_no_marker_is_unknown` で印が無い場合を 2 と固定しており、drift は 1、一致は 0 である。字面は事実と合う。

**面の生成器は影響を受けない。** `face_adr.rs` は `adr/schema.yaml` を読まない（schema への参照が 1 件も無い）。`face_note.rs` の `id_pattern` はコメントの中の説明語で、file を読んでいない。判断の記録の面・設計ノートの面は、欄の決まりの file が生成物になっても変わらない。帰結が面に触れていないのは、抜けではなく正しい。

**readable.html への影響はごく小さい。** `render.rs` は見出しの中で「欄の決まりは `adr/schema.yaml`」と字面を出すだけで、file の中身を読まない。字句を「生成物」に合わせるかどうかの問題に留まる（readable.html 自体の退役は別便・s2-07l.467 待ち）。

**床は現に緑で、ADR-9 は床の母集団に入っている。** worktree で `folio check` を回すと「合格（違反 0・まだ分からない 0）」。scratchpad に写した設計文書の ADR-9 の `plain` に架空の英字語を 1 つ入れると「[adr] ADR-9 plain: 語彙に無い英字の語「zqxwv」」が立つ。つまり ADR-9 は欄の決まり・裸の英字語・参照 id の検査を実際に通っている（問い 5 の機械の部分）。

### 反証（抜けている影響）

**(1) 凍結 fixture の写しが 16 本ある。** `tests/fixtures/*/adr/schema.yaml` が 16 本、いずれも 2,199 byte の「欄の決まりの最小の写し（schema 節 = 床の定数・`*_note` の欄は持たない）」である（fixture 自身の先頭の注の逐語）。現行の検査は `strip_notes` した schema 節だけを床の定数と突き合わせるので最小の写しで足りるが、決定の「folio check は…「導出との byte 一致」に置き換える」を字義どおり当てると、この 16 本はすべて落ちる。逃げ道は 3 つで、どれを採るかを判断の記録が書いていない。

- 16 本を 24,933 byte の完全な生成物に差し替える。1 本あたり幅 120 の正規化で約 208 行、16 本で約 3,300 行。便の上限（S 100 行 / M 300 行）に収まらない。
- byte 一致の検査を `folio schema --check` だけが持ち、`folio check` の per-dir の検査は欄単位の突き合わせのまま残す。fixture は最小の写しを保てるが、決定の「置き換える」の字面が偽になる。
- 検査の適用を設計文書の置き場（`design-intent/`）に限り、fixture の dir では欄単位に落とす。これも決定の字面を直す必要がある。

**(2) 導出の範囲が決まっていない。決めると P-5.5 に触れる。** `adr.rs` / `note.rs` の `FLOOR` が覆うのは schema 節の `*_note` でない欄だけである。file の残り（先頭の注・`meta`・`*_note` 群・`plain`、設計ノート側はさらに `mapping`）は覆っていない。`design-note/schema.yaml` 自身が「meta・mapping・plain は schema 節の外（床の定数ではない）」と宣言している。決定の「値も注も正本は実装の定数 1 か所」と帰結の 4 つ目（`*_note` を実装側に持つ）は `*_note` までは決めているが、`meta` と `mapping` と `plain` を決めていない。file 全体を byte 一致にするならこの 3 つも実装へ移り、そこには **裁定の記録** が入っている。逐語:

> `type_enum_ruling: {basis: [ADR-3, FR9, FR12], ruling: f2-648 notes 2026-09-17 06:53 JST（逐語「承認する」・対話面 R-8・f2-648.7 の取り込みの承認）, ruled_at: 2026-09-17}`

P-5.5 は「原則と裁定の正本は設計文書」と定める。裁定の正本を実装の定数へ移すのは、この条に正面から反する。したがって範囲は「schema 節だけ」に限るのが筋で、それを決定に書く必要がある（問い 2 の案 e）。

**(3) 凍結 fixture の期待の字面 15 件が変わる。** `tests/floor_cases.yaml` の 15 case は `expect_msg` に「schema.owner が床の定数と違う」等の欄の道を含む。byte 一致に変えると床の出す文言が変わるので、134 case のうち 15 件の期待を書き換えることになる。凍結 anchor（P-10.1）を実装の出力に合わせて書き換える作業なので、便の write-set に明示して取り込みの審査で読む必要がある。帰結の「便で運ぶもの」の列に入っていない。

**(4) 同じ形が `ceiling.yaml` に残り、ADR-10 がそれを維持すると書いている。** `ceiling.rs` は `CEILING_TOP_LEVEL` / `VERDICT_VALUES` / `VIEWPOINT_IDS` / `DOCUMENT_IDS` / `FINDING_REQUIRED` / `PLACE_REQUIRED` / `REFUTE_VALUES` / `RECORD_REQUIRED` / `BUNDLE_CONTENTS` を床の定数で持ち、`ceiling.yaml` は同じ一覧を data 側に手書きで持ち、床が「一覧が床の定数と違う」で落とす。F-1 が名指した形と同型である。しかも同日提案の ADR-10 の決定 (2)③ は「文書の一覧・観点の一覧・所見と記録の欄の決まり・3 値・重さの値域・束の要約値の規則は変えない（便 37 の床の定数と一致したまま）」と、この形の維持を明記している。ADR-9 の帰結 3 つ目は「天井の 1 周目の止める所見（文書どうしの整合 F-1）は本判断の発効と便の着地で解消し」と書くが、解消するのは F-1 が名指した場所（ADR-1.decision）だけで、同じ形は他に残る。2 周目で同型の所見が `ceiling.yaml` に対して立つ見込みが高い。同様の形は入口（`entrance.rs`）・相談窓口（`intake.rs`）・要件書の節の一覧（`check.rs`）にもある。

**(5) 天井の束には生成物が入り、正本は天井の読む文書の一覧に無い。** `bundle.rs` の `copy_sources` は、文書 id が dir 形（`adr/`）のとき「直下の .yaml を名の byte 順に全部」写す。つまり `adr/schema.yaml` は天井の束に入る。ADR-9 の後、審査役は生成物を読むことになり、その正本（実装の定数）は `ceiling.rs` の `DOCUMENT_IDS`（憲法・規則の表・語彙・要件書・入口・相談窓口・判断の記録・設計ノート・天井の正本の 9 つ）に無い。欄の決まりの中身に対する所見が出ても、直す先を審査役が読めない。帰結か天井の正本の次の版で扱いを決める必要がある。

**(6) ADR-2 の決定にも同じ字面が在るのに、帰結が ADR-1 しか挙げていない。** ADR-2 の決定 (5) の逐語は「写しの取り方と範囲の下限・列の根・置き場・印が床の定数と一致すること（欄の決まりの file はその写し＝data 側で動かせない）」である。ADR-9 が外すのはまさにこの「写し」なので、ADR-2 の決定の一部も本判断が引き取ることになる。帰結 2 つ目は ADR-1 にしか触れていない。

**(7) 人が読む写しの体裁が変わる。** 現行の欄の決まりは flow の表（`{required: [...], optional: []}`）と block を混ぜ、引用符の付け方も手で整えてある。生成器から byte 一致で出すなら、生成器の canonical な体裁に一度書き換わる。この file は「人が読む写し」なので、見た目が変わることは帰結に書いたほうがよい。

### まだ分からない

- 便の大きさが上限に収まるかは、(1) と (2) の選び方が決まるまで測れない。schema 節だけを生成区間にし、fixture の写しは欄単位のままにするなら、運ぶのは `folio schema` の実装と `*_note` の移動（`adr.rs` へ約 15 KB、`note.rs` へ約 12 KB の日本語の文）で、便 2 本に割るのが現実的に見える。

## 問い 5: 形式は欄の決まりを満たすか

### 支持

**機械の検査は通っている（実測）。** worktree で `folio check` を回して「合格（違反 0・まだ分からない 0）」。ADR-9 が母集団に入っていることは、scratchpad の写しで `plain` に架空の英字語を入れると `[adr] ADR-9 plain: 語彙に無い英字の語「zqxwv」` が立つことで確かめた。したがって次はすべて満たしている。

- 必須の欄（id・title・status・date・context・decision・options・basis・retreat・plain）が揃い、非空の欄（title・context・decision・plain）が空でない。
- 案は 3 つで、採用は 1 つ（`options_rule: {min: 2, adopted: 1}`）。各案に id・name・text・verdict・reason が在る。
- `retreat.kind` が値域（spike / measure / ruling）の中の `measure` で、`condition` が非空。
- `status: proposed` なので承認欄が無くてよい。
- 基準（basis）の各項が id の形で、行き先が全部解ける（P-2・P-5・P-6・P-10・P-14・N-3・ADR-1・ADR-2・ADR-8・FR6）。
- 裸の英字語が 0。本文に出る英字（folio・file・data・byte・schema・adr.rs・note.rs・Python・YAML ほか）は語彙の identifiers か field_terms に在るものだけで、床が落としていない。

**平易文（plain）は非エンジニアが読める。** 「ファイルが 2 枚あり、今は機械の中の決まりと人が書いたファイルの両方に同じ中身があって、機械が『1 文字でも違えば止める』形でした」→「人が書くのをやめて、機械の決まりから folio が自動でそのファイルを作る形にします」→「読める写しは残りますが、直すときは機械の決まりの側を直します」。専門語は「憲法」「機械」「ファイル」だけで、判断の要点（何をやめ、何に替え、どこを直すことになるか）が全部入っている。ADR-1・ADR-2 の平易文と同じ水準。

### 反証

**基準の P-2 が本文のどこにも効いていない。** P-2 の規範文は 1 つの生成器・手書きのページを導線に置かない・design token・部品目録の 4 つで、ADR-9 の context・decision・options・consequences のどこにも現れない。id は解けるので床は落とさないが、基準は「その判断が寄りかかった条」を並べる欄である。使っていないなら外し、P-2.2（手書きのページを配信先と入口の導線に置かない）を類推の根拠として使うなら本文に書く。

**「配信先」の語が folio2 の既存の用法とずれる。** 決定は「配信先と導出の byte 一致を数え」と書く。folio2 で「配信」は `folio serve` と `folio build --out` の出し先を指し、憲法 N-6 の主語でもある。ここで指したいのは `design-intent/adr/schema.yaml` という正本の置き場であって、配信の出し先ではない。語彙に「配信先」の項は無い。「置き場の file と導出の byte 一致」等に言い換えたほうが、読み手が取り違えない。

**平易文が問い 4 の (1)(2) を含まない。** これは今の決定の字面に対しては正しい（平易文は決定を写すものなので）。決定を直したら平易文も「機械の決まりの側に移すのは欄の決まりの部分だけで、誰がいつ決めたかの記録は文書の側に残す」の 1 文を足すとよい。

### まだ分からない

- 現行の binary は 2026-09-19 17:51 の build で、`folio check` の結果はその時点の実装に対するものである。実装が変わればやり直しが要る。

## 発効を止める重さの指摘

**G-1. P-5.5 に対する読みが決定にも案にも無く、逆向きの案が options に立っていない。**
P-5.5 の「機械が執行する規則の正本は型付きデータとし、置き場をこの 2 面に限る。」に対し、ADR-9 は正本を実装の定数に置く。実装の型付き定数が「型付きデータ」に当たるかを判断の記録が宣言していないため、F-1 を閉じても P-5.5 の側に同型の穴が開いたままになる。しかも ADR-9 は同じ難点（実装の定数だけで P-5.1 を満たす説明が要る）を退けた案 b の却下理由としては書いており、採用案について書いていない。反証役が先に挙げた 2 つの是正の向きのうち、P-5.1 の括弧が字義で名指すほう（欄の決まりの file を正本にして実装が読む）は案として立っていない。直しは、決定への 1 文（実装の型付き定数を P-5.5 の型付きデータの 1 つとして扱う）と、案 d の追加（N-3.1 と ADR-1 の実測を理由に退ける）である。→ 問い 1・問い 2。

**G-2. 導出の範囲（file 全体か schema 節だけか）が決まっておらず、file 全体だと裁定の正本が実装へ移る。**
床の定数が覆うのは schema 節の `*_note` でない欄だけで、`meta`・`mapping`・`plain` と先頭の注は覆っていない（設計ノートの欄の決まりが「meta・mapping・plain は schema 節の外（床の定数ではない）」と自ら宣言する）。file 全体を byte 一致の生成物にすると、`meta.type_enum_ruling`（持ち主の裁定 id と逐語と日付）の正本が実装へ移り、P-5.5 の「原則と裁定の正本は設計文書」に反する。憲法の生成区間（P-14）と同じく「schema 節だけを生成区間にする」と決定に書けば塞がる。→ 問い 4 (2)。

**G-3. 決定の「folio check は…byte 一致に置き換える」は、凍結 fixture の 16 本の最小の写しに当てると偽になる。**
`tests/fixtures/*/adr/schema.yaml` は 16 本すべてが 2,199 byte の最小の写しで、`*_note` を持たない。byte 一致を per-dir の検査に当てると 16 本が落ち、完全な写しに差し替えると約 3,300 行になって便の上限に収まらない。検査の適用範囲（`folio schema --check` は設計文書の置き場だけ／`folio check` の per-dir は欄単位のまま、など）を決定に書かないと、便を受ける側が黙って選ぶことになる。→ 問い 4 (1)。

## 直すとよい指摘

**D-1. 撤退条件の 2 種を「同じ種類の失敗」と呼んでいる。** R-7 の `same_failure` は（検査の id・判定・対象の path）の 3 つ組で、この 2 つは別種である。ADR-2 は同じ場面で「2 つは R-7 の same_failure では別種なので、別々に数える」と明記した。同じ書き方に揃える。→ 問い 3。

**D-2. 2 つ目の事象（便の受付が止まった回数）が R-7 の 3 つ組に写せない。** 器の側の出来事なので、何を 1 件と数えるかを本文に書く。→ 問い 3。

**D-3. 同じ形が `ceiling.yaml`（ほかに入口・相談窓口・要件書の節の一覧）に残る。** 帰結 3 つ目の「F-1 は解消し」は、F-1 が名指した場所については正しいが、同型の配置は残る。ADR-10 の決定 (2)③ はその維持を明記している。帰結に「同じ形が残る file と、その扱いを別の判断で決める」と書く。→ 問い 4 (4)。

**D-5. `tests/floor_cases.yaml` の 15 case の期待の字面が変わる。** 帰結の「便で運ぶもの」に入れる。凍結 anchor を実装の出力に合わせて書き換える作業なので、取り込みの審査で必ず読む対象として明示する。→ 問い 4 (3)。

**D-6. ADR-2 の決定 (5) にも同じ字面（欄の決まりの file はその写し）が在る。** 帰結 2 つ目に ADR-2 を足す。→ 問い 4 (6)。

**D-8. 「配信先」の語が folio2 の既存の用法（serve / build の出し先・N-6）とずれる。** 語彙に項が無い。置き場の file を指す語に言い換える。→ 問い 5。

## 総括

ADR-9 の向き（欄の決まりの file を実装の定数からの導出物にする）は正しい。天井の 1 周目の止める所見 F-1 は、独立の文脈の反証役が支持し、本審査でも逐語を追って支持する。P-6.3・P-6.4・P-6.2 との両立は明確で、N-3.1 の性質（data 側から緩められない）も導出後に保たれる。退けた案 b・c の却下理由も、引く逐語の噛み合わせを除けば事実に基づく。撤退条件は行き先（案 b）を持ち、`measure` の型に合っている。形式は床が実測で緑であり、平易文は非エンジニアが読める水準にある。それでも、このまま発効させるべきではない。理由は、本判断が答えるべき問い——「規則の正本を実装に置いてよいのはなぜか」——に判断の記録が答えていないからである。P-5.5 の「置き場をこの 2 面に限る」に対する読みを宣言せず、P-5.1 が字義で名指す逆向きの案を options に立てないまま採用案を選んでいる。しかも同じ難点を、退けた案の却下理由としては書いている。加えて、導出の範囲を決めていないために「file 全体」と読むと裁定の正本まで実装へ移り、「folio check を byte 一致に置き換える」を字義どおり読むと凍結 fixture 16 本と衝突して便が組めない。3 点はいずれも決定文への 2〜3 文と案 1〜2 件の追加で塞がり、判断そのものを変えない。塞いだうえで発効させるのがよい。

発効を止める重さの指摘は 3 件、直すとよいの指摘は 11 件。所要時間は約 15 分（2026-09-19 17:50 頃〜18:05 JST・読み取りと実測の tool 呼び出し 13 回・repo への書き込みは本 file のみ）。

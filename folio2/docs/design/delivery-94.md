### (b) 出力の形（標準出力・repo へは書かない）

`folio graph --print --dir <正本の置き場>` が次の 3 つを標準出力へ書く。設計ノート §6.1 が定める形と同じで、1 行はタブ区切り、最後の行も改行で終わる。

```
# 節点（1 行 = id / 種類 / file / 題 36 字・タブ区切り）
A-1	条	constitution.yaml	消す・外へ出す・使う は確認してから
A-1.1	規範文	constitution.yaml	既存の文書やデータを消す、外へ出す、外部の道具や鍵を使う（課金を含む）操
# 辺（1 行 = 端 / 端 / 型・タブ区切り）
A-1	A-1.1	in-article
A-1	A-4	relations.articles
# 節点 198・辺 777・型 15・端が節点でない参照 27
```

- **出力先は標準出力だけで、`design-intent/preview/` にも `<dir>` の下にも file を書かない。** 索引の中身は版管理に置かない毎回組み直す導出物だからである（ADR-13 決定 (1) の末尾・決定 (4)）。書かないので N-1.1（回復不能な削除）にも触れない。
- **形は 1 つの file に収まるタブ区切りの表にする。** YAML にしない理由は 2 つ。① 索引は人も AI も 1 度に読み下す表で、入れ子を持たない（節点 4 欄・辺 3 欄）。② YAML にすると `design-intent/graph.yaml` と同じ拡張子の面が 2 つ（人が書かない正本と、書かない導出物）できて、どちらが正本かが字面で見分けられなくなる（P-6.3 の向き）。タブ区切りなら `cut -f1` で id だけを取れて、AI にも OS の道具にも安い。
- 節点の並びは **id の byte 順**、辺の並びは **（端・端・型）の 3 つ組の byte 順** とする。同じ 3 つ組は 1 本にまとめる（重複は出さない）。決定的であること以外の含みは持たせない。
- 題は **空白の連なりを 1 つに畳み、前後を落とし、Unicode の字で 36 に切る**。欄はその種類ごとに決まっていて、条と目的と要件と非機能要件と受入基準と制約と判断の記録は `title`、規範文は `text`、規則の表の行は `what`、登場人物と出力は `name` である。**畳んでから切るので、正本を読む道具が改行や行頭の空白をどう持つかで字が変わらない。**
- **要約の 1 行は最後に置く。** 中身は 節点の数・表に出た辺の数・表に出た辺の型の数・端が節点でない参照の数 の 4 つ。**端が節点でない参照を黙って捨てない**のは条 P-4.2（判定できないものは表に出す）と要件 NFR3（参照は必ずつながる）の向きである。
- 索引が組めない（正本が読めない・最上位が欄の表でない）ときは、**表を 1 行も出さずに「まだ分からない」（終了コード 2）で終える**（ADR-13 決定 (4)・条 P-4.1 / P-4.2）。空の索引を合格として出さない。

## 1. 責務の 6 層

| 層 | 責務 | 何を知っているか |
| --- | --- | --- |
| 0 土台 | 文書を何も知らない共通の型と計算 | 何も知らない |
| 1 読む | 正本の byte を型に直す。閉じた一覧・値域・床の木の型を持つ | 正本の形 |
| 2 検査する | 型に直したものを決まりに照らして数える | 正本の形 + 決まり |
| 3 導出する | 正本から別の型付きの出力を作る（生成区間・索引・束・印・anchor・支度表） | 上記 + 出力の形 |
| 4 面に出す | 人が読むページ（HTML）と図の本体（SVG）を書く | 上記 + 見た目 |
| 5 配る | 命令の入口と、生成物を置き・見せ・知らせるところ | 全部 |

**向きの決まり**: file は自分より下の層だけを名指す。同じ層どうしの名指しは許す。

総点検の設計ノート §3-d は 5 層（読む → 検査する → 導出する → 面に出す → 配る）を挙げた。土台を 1 つ足したのは、`verdict.rs`（判定の 3 値と終了コード）と `sha256.rs`（要約値の計算）が正本を 1 字も読まず、文書の形を何も知らないためである。読む層に入れると、その層の責務を「正本を型に直す」と言えなくなる。

層 5 の責務に「命令の入口」を足したのは、`main.rs` が置きも見せも知らせもしないのに層 5 に在るという食い違いを消すためである（審査役の直し 1）。

**面の中の割り**: 便 115・便 116 が切り出す「正本を読んで面の文脈を組む」部分は、面の口（`anchor`・`esc`・`tier_label` ほか）を呼び、関係の欄からはリンク（HTML）も組む。層 1 の定義に当てはまらないので、新しい file は**層 4** に置く（同じ層の中の割り）。向きの決まりは同じ層を許すので、塞がりは開き、上向きの辺も増えない（審査役の直し b-1-4）。

**層 1 の定義と実測が合う時点**: 「閉じた一覧を持つ」という層 1 の定義に実測が追いつくのは、§4 の便 108（部品目録の閉じた一覧）と便 109（入口の棚と設計ノートの状態の閉じた一覧）の後である。それまでは 2 つの閉じた一覧が検査の層と面の層に在る（審査役の直し 2）。

区間を移すだけでは組み立てが通らない。写しの repo で 11 本を当てたところ、**見え方（私か、同じ道具の中で公開か）が広がった箇所は合計 183** だった。内訳の大きいものは次のとおり。

**既存の歯も 1 本だけ直す**。便 109 は、前の割り（便 87）を字面で固定している歯 `f87_face_is_split_and_under_the_cap` を直す。入口の棚の閉じた一覧がその歯の見る file から降りるので、直さないと落ちる。改訂 b の「既存の歯を 1 本も動かさない」は偽だった。

この歯は前の割りを字面で固定する**構造の歯**で、便 106 が足す境界の歯（`p106_`）も同じ性質である。構造の歯は、それが固定している割りを変える便が自分で書き直せる＝「便が触れない基準」ではない（§5-a の 1 と同旨）。便 109 の訂正は、その形が実際に起きた 1 例目である。

### 4-e. 床の定数を 2 本しか降ろさない理由

責務の線（床の定数は読む層・検査は検査の層）は**床の木 9 本すべてに一様に掛かる**。本判断が運ぶのは 2 本（判断の記録・設計ノート）で、選んだ理由は**余地が 300 未満だから**である。残り 5 本（天井・入口・相談窓口・規則の表・正本 7 file）は余地が足りている（499 以上）ので本判断では運ばず、後続に置く。**どれを先に運ぶかを余地で決めることと、境界を余地で決めることは別である**（審査役の直し 3）。

なお、便 110 が降ろす天井の 8 本は床の木ではなく、所見と束の閉じた一覧（欄の集合・値域）である。降ろす理由は「束の組み直しが使うから」で、上の 9 本の数には入らない。

## 5. 境界の歯（`crates/folio/tests/modules.rs`・便 106 で新設）

層の割り当てと、まだ降ろしていない上向きの辺の一覧は、**歯の側**が型付きデータで持つ。実装の側に置いて歯がそれを読む形にすると、実装が自分で自分を採点することになる。

```rust

const LAYERS: &[(&str, u8)] = &[

    ("yaml", 1), ("constitution_enums", 1), ("floor", 1),
    // ... 44 行から始めて 54 行まで増える ...
];

/// まだ降ろしていない上向きの辺（ADR-15 決定 (4)）。凍結した実測であって許可ではない。
/// 行を足す書き換えは認めない（足すなら ADR-15 を改訂する）。
const REMAINING_UPWARD: &[(&str, &str)] = &[
    ("adr", "schema"), ("note", "schema"), /* ... 20 対から 0 対へ ... */
];
```

| 歯 | 何を数えるか | 落ちるとき |
| --- | --- | --- |
| `p106_layers_cover_every_module` | `LAYERS` の file 名の集合が、`src/main.rs` の区切りの宣言（`mod <名>;`）の集合と一致する | 新しい file が層を持たない／消えた file が表に残っている |
| `p106_edges_point_down` | 注釈を剥がした `src/*.rs` を走査して辺を集め、層が上がる対の集合が `REMAINING_UPWARD` と**一致**する | 上向きの辺が 1 本でも増えた／減ったのに一覧を直していない |

2 本目は集合の一致を見るので、辺を足しても減らしても落ちる。無効化の旗も「今回だけ」の口も持たない（N-3.1）。

### 5-a. この歯が言えないこと（限界）

1. **独立した anchor ではない。** 層の割り当ても辺の一覧も、実装の側と**同じ便・同じ書き手**が同じ書き込み範囲の中で書き直す。file が違うだけで、条 P-10.1 が求める「生成側からも検査側からも独立した」凍結 anchor にはならない。ADR-15 はこれを「凍結した実測」と位置づけ、独立性の主張は取り下げている（審査役の直し 9・18）。
2. **注釈を剥がさないと偽の辺が出る。** 今の写しでは剥がしても辺の計は変わらないが、区間を降ろした先の file の説明文が偽の辺を作る場面を、写しでの適用で実測 2 件見た（`phase.rs` の説明文の `anchor::check_anchor`・`ceiling_src.rs` の説明文の `findings::refute`）。歯は剥がしてから数える。
3. **区切りを宣言する入口の辺は接頭辞なしで書かれる。** `main.rs` は 43 本を宣言し、本文で 16 の区切りを接頭辞なしで名指すが、`crate::` は 1 回しか書かない。数えないと 43 節点の図の上の「0」になる。歯は `main.rs` だけ接頭辞なしも数える（審査役の直し 10）。
4. **再輸出を挟んだ名指しは見えない。** 今の写しに 1 例ある（`face.rs:483` が `face_labels.rs` を丸ごと再輸出し、呼ぶ側の真の行き先は `face_labels.rs`）。便 113 自身も再輸出を使う。歯は字面を見るので、再輸出を挟めば上向きの辺を書かずに同じ依存を作れる。**この歯が言えるのは「字面の上で上向きの辺が無い」までである。**
5. **区間が接頭辞なしで取り込んだ名を見ない。** `use` で取り込んだ名を接頭辞なしで呼ぶと、その依存は字面に現れない。区間を切り出すとその名を新しく名指すことになり、そこで初めて辺が生える。改訂 b の列はこれで 4 便ぶん外れていた。**便の契約を書く前に、区間が使う名のうち区間の外に定義があるものを列挙すること**（審査役の b-1-5）。列挙の確かめ方は、写しに区間を切り出して `cargo build` を撃つことである。
6. **全部の便の合流点になる。** 辺を動かす便はどれも `tests/modules.rs` を書き込み範囲に入れるので、並行して運ぶ便が直列になる。ADR-15 が見込む「重なりが減る」に逆向きに働く（審査役の直し 11・20）。

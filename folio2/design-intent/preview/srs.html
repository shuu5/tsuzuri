要件書 (SRS) folio2 — M0（最初に動く形）

AI と相談して必要な文書だけを決め、同じ見た目で 3 枚を出し、機械が検査して黙らない

M0 = いちばん小さい完成形。ここに書いた要件が満たされたら「動いた」と言う。

要

この文書が約束すること（1 文）

持ち主が易しい質問 5 つに答える（答えなくても推奨で進む）と、入口・憲法・要件書の 3 枚が同じ見た目で生成され、機械検査の結果が必ず表示される。

状態未承認のため拘束力なし → 持ち主の承認で発効（承認欄へ）

ゴール

「これができたら成功」を先に決める

持ち主が挙げた 4 つの不満を裏返したもの。以降のすべての要件は、この 4 つのどれかのためにある。

はじめて読む人 2/3入口の「読む順番」で選んだ道のうち、「はじめて読む人」の 2 番目。1 番目は憲法 §0、3 番目は要件書 §3 の図 2。次は → §3 の図 2（道具が通す 7 段）

GOAL 1

相談して決められる

「どの文書が要るか分からない」を無くす。最初と途中の両方に窓口がある。

GOAL 2

見た目が揃う

入口も要件書も同じ品質・同じ様式。割れたページを作れない。

GOAL 3

AI が自分で動き出す

持ち主が道具を起動しなくても、AI が必要なときに folio を使う。

GOAL 4

壊れにくい道具

bash の寄せ集めをやめ、1 つの実装（Rust）に置き換える。検査は黙らない。

要件書（M0）›03 機能要件 3/8

機能要件

8 つの機能要件 — いつ・何をするか

まず図 2 で、道具が 1 回で通す 7 段のどこを各要件が決めているかを見る。各要件は「正確な要件文 → やさしく言うと → どう確かめるか」の順。

はじめて読む人 3/3ここが最後。戻るなら → 入口

凡例:

MUST = 必ず守る ／ SHOULD = 強い推奨（外すなら理由が要る）／ SHALL = 要件文の中の「〜する」（守る約束）／ SHALL NOT = 「〜してはならない」

WHEN 〜のとき ／ WHILE 〜の間 ／ IF … THEN もし〜なら ／ 何も付かない = つねに（用語 · EARS要件文の書き方の型。「〜のとき」「〜の間」「もし〜なら」「つねに」で、いつ守るかを示す。 用語集で見る → の型）

実際に動かして確かめる（Test） = 道具を走らせて結果を見る ／ 目で見て確かめる（Inspection） = 人が画面や設定を見て確かめる。各要件の「確かめ方」に、どちらで確かめるかを書いてある。

FR1

相談窓口（intake）

MUST〜のとき

WHEN 持ち主が folio intake を実行したとき、folio は 5 問以下の易しい質問を推奨回答つきで提示し、回答から文書の集合を写像して用語 · 支度表相談窓口の結果。どの文書を持つか・推奨で進めた項目を 1 枚にまとめたもの。 用語集で見る → 1 枚を生成 SHALL する。

やさしく言うと「何の文書が要るか」を AI と決める入口。質問は 5 つまで、どれにも「おすすめ」がついています。結果は支度表 1 枚。

実際に動かして確かめる（Test） 決まった回答 5 つを入れ、支度表が期待どおりか比較する（AC1）GOAL 1（相談）・報告 軸 2憲法 P-1（判断は人）図 2 ① 相談して決める図 2 ② 支度表が出る図 1 持ち主（非エンジニア）

FR2

答えが無くても止まらない

MUSTもし〜なら

IF 質問への回答が得られない THEN folio は推奨回答で進み、支度表に「推奨で進めた項目」を別枠で明示 SHALL する。

やさしく言うと忙しくて答えられなくても作業は止まりません。ただし「おすすめで決めた所」は支度表で分かるようにします。

実際に動かして確かめる（Test） 無回答で実行し、別枠に全項目が出ることを見る（AC1）GOAL 1（相談）・裁定 #1（非同期既定）憲法 P-1 と衝突しない線（推奨で進み、支度表で覆す）図 2 ① 相談して決める

FR3

気づかせる 1 行

SHOULD〜の間

WHILE design-intent が未整備である間、セッション開始時に folio は 1 行だけ案内を出す SHALL。opt-out は設定 1 key、1 project につき 1 回のみ。

やさしく言うと文書がまだ無い project では、AI のセッションが始まったときに一言だけ知らせます。うるさければ「止める設定」1 か所で切れます。

実際に動かして確かめる（Test） 未整備 / 整備済 / opt-out の 3 状態で出力行数を数えるGOAL 3（自動）・報告 軸 2「沈黙反転」図 2 ① 相談して決める図 1 AI セッション（Claude Code）

FR4

3 枚を 1 つの生成器で出す

MUSTつねに

folio は用語 · 正本元になる唯一のファイル。ページはここから作った写し。 用語集で見る →（YAML）から入口・憲法・要件書の 3 面を、単一の用語 · 生成器生成物 = 正本から機械が作ったもの（手で直さない）。生成器 = それを作る係。 用語集で見る →と単一の 用語 · design token色・字の大きさ・余白などの元の値。1 か所で決めて全ページが使う。 用語集で見る → で生成 SHALL する。

やさしく言うと3 枚とも同じ係が同じ材料（色や字の大きさの元の値と、決まった部品）で作るので、見た目が割れません。

実際に動かして確かめる（Test） + 目で見て確かめる（Inspection） NFR2 の数値で判定する（AC2）GOAL 2（揃う）・憲法 P-2 / P-6図 2 ④ 3 枚を出す図 1 → 3 面（入口・憲法・要件書）

FR5

検査結果を必ず返す

MUSTつねに

folio は生成のたびに構造の用語 · 床（floor）床 = 機械が決定的に検査する層（合格は「壊れていない」の意味）。天井 = AI が意味を検査する層。 用語集で見る →を実行し、結果を Pass / Fail / Pending の 3 値で返す SHALL。実行できなかった検査を Pass と表示しては SHALL NOT ならない。

やさしく言うと「合格・不合格・まだ分からない」の 3 つのどれかを必ず表示します。「分からない」を「合格」にすり替えません。

実際に動かして確かめる（Test） 床を故意に壊して「まだ分からない」になることを見る（AC3）GOAL 4（壊れない）・憲法 P-3 / P-4図 2 ⑤ 床の検査図 1 検査の結果（3 値）図 3 合格 — 壊れていない

FR6

憲法を AI の手元に届ける（inject）

MUST〜のとき

WHEN folio inject --write が実行されたとき、folio は憲法の機構条を CLAUDE.md の用語 · 生成区間CLAUDE.md の中で、機械が書き換える印のついた範囲。手で直さない。 用語集で見る →へ書き込む SHALL。--check は区間と正本の差分を検出し、差があれば非 0 で終了 SHALL する。

やさしく言うと憲法の「機械が守るべき条」を、AI が毎回読む場所（CLAUDE.md）に写します。ずれたら知らせます。

実際に動かして確かめる（Test） 区間を 1 字変えて --check が非 0 になることを見る（AC4）GOAL 3（自動）・憲法 P-5（散文だけの規則は規則ではない）図 2 ⑥ AI の手元へ配る憲法 図 1 ④ 版を上げ、再注入する

FR7

組み立てて、見せる（build / serve）

MUST〜のとき

WHEN folio build が実行されたとき、folio は全面を配信先へ生成 SHALL する。folio serve は 用語 · tailnet自分の端末どうしだけがつながる私設ネット。ここ以外に公開しない。 用語集で見る → 上でのみ配信 SHALL し、公開ネットへ bind しては SHALL NOT ならない。

やさしく言うと「作る」と「見せる」の 2 つの命令。見せる先は社内ネット（tailnet）だけ。

実際に動かして確かめる（Test） + 目で見て確かめる（Inspection） tailnet の住所が無いとき起動を拒むことを見るGOAL 2（揃う）・制約 CON3図 2 ⑦ 組み立てて、見せる

FR8

途中で足す窓口

SHOULD〜のとき

WHEN 持ち主が文書の追加・削除を求めたとき、folio は差分だけを対象に intake を再実行し、支度表を更新 SHALL する。

やさしく言うとあとから「やっぱりこの文書も」となっても、最初からやり直さず、差分だけ相談します。

実際に動かして確かめる（Test） 既存の支度表 + 追加 1 型で、質問が差分だけになることを見るGOAL 1（相談）（途中で足す窓口）図 2 ① 相談して決める図 2 ② 支度表が出る

非機能要件

3 つの非機能要件 — 数で測れる約束

機能ではなく「どれくらい」を決める。値は 憲法 §5 rules と同じ表から来る。

凡例:

MUST = 必ず守る ／ SHOULD = 強い推奨（外すなら理由が要る）／ SHALL = 要件文の中の「〜する」（守る約束）／ SHALL NOT = 「〜してはならない」

実際に動かして確かめる（Test） = 道具を走らせて結果を見る ／ 目で見て確かめる（Inspection） = 人が画面や設定を見て確かめる。各要件の「確かめ方」に、どちらで確かめるかを書いてある。

NFR1

AI へ常時渡す説明文の上限

MUSTつねに

folio が常時注入する説明文（agent と skill の名前 + 説明）の合計は rules R-1 の値以下 SHALL（現在 ≤ 2,000 字・測り方の凍結後に再計測）。

やさしく言うとAI が毎回読まされる「道具の説明文」の量に上限を置きます。v1 ではこれが膨らんで遅く高くなりました。

実際に動かして確かめる（Test） 計測スクリプトが CI で数えるGOAL 3（自動）・GOAL 4（壊れない）・憲法 N-3・rules R-1・spike 2図 2 ⑥ AI の手元へ配る

NFR2

見た目の材料は 1 か所から

MUSTつねに

全生成面の design token は単一の定義に由来する（100%）SHALL。用語 · 部品目録ページを組み立てる部品（表紙・章帯・カード・図）の一覧。ここに無い部品は使えない。 用語集で見る →に無い class は 0、床が掛からない HTML 面は 0 SHALL。

やさしく言うとどのページも、色や字の大きさ・部品を同じ 1 か所から取ります。「このページだけの飾り」は 0 個。検査（床）が掛からないページも 0 枚。

実際に動かして確かめる（Test） 全面の class を部品目録と突合する（AC2）GOAL 2（揃う）・憲法 P-2・rules R-3図 2 ④ 3 枚を出す

NFR3

参照は必ずつながる

MUSTつねに

文書間の参照 id（要件・条文・判断・受入基準）の未解決は 0 SHALL。

やさしく言うと「FR3 を見よ」「P-2 による」と書いたら、その番号は必ず実在します。行き先の無い番号は 0 個。

実際に動かして確かめる（Test） 参照 id を全部集め、実在を数えるGOAL 4（壊れない）・憲法 P-7・rules R-4全段に掛かる（図 2 の注記）

要件書（M0）›05 受入基準 5/8

受入基準

4 つの受入基準 — 何を見せられたら「できた」か

M0 で測れるものだけ。どれもまだ確かめていない（灰色 = 未検証）。持ち主の承認待ちはこの 4 件。

決める人 1/3次は → 憲法 §3 確認してから変える

AC1 未検証

決まった 5 つの回答で支度表ができ、未回答の項目は別枠に出る

やさしく言うと決まった答えを 5 つ入れると「何を作るか」の表が出て、答えなかった項目は別の枠に分けて出る。それを見せてもらえたら OK。

FR1・FR2 を確かめる。回答をゼロにしても止まらない。

AC2 未検証

3 面のすべての class が部品目録に存在し、目録に無い class は 0

やさしく言うと3 枚のページに、部品表に載っていない飾りや、決まった材料以外の色が 1 つも無いことを、機械が数えて見せる。

FR4・NFR2 を確かめる。この見本 3 面は既にこの条件で作ってある。

AC3 未検証

床を壊した状態で「まだ分からない」が表示され、合格にならない

やさしく言うとわざと検査を壊した状態で道具を走らせ、「まだ分からない」と表示されて「合格」にならないことを見せる。

FR5 を確かめる（図 3）。「分からない」が「合格」に化けないことの証拠。

AC4 未検証

CLAUDE.md の生成区間を 1 字変えると --check が非 0 で終わる

やさしく言うとAI の手元にある憲法の写しを 1 文字だけ書き換えて道具を走らせ、道具が「ずれている」と言って止まることを見せる。

FR6 を確かめる。憲法と AI の手元がずれたら必ず気づける。

凍結しないもの

「60 分以内にできる」「300k token 以下」は、ここには書かない。測定の仕組みが違うので、M1 の実地試験（非エンジニア 1 回）で初めて数値を決める。

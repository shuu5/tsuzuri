# folio2 — project instructions

本 file は folio2 の憲法（`design-intent/constitution.yaml` が正本）の前文と規範文を写した生成区間だけを持つ。作法の SSOT は `design-intent/`（憲法・rules・語彙・要件書 M0）と `.beads/PRIME.md`（台帳の運用）にある。
生成区間は `folio inject --write`（正本 = `design-intent/constitution.yaml` と `design-intent/rules.yaml`）の生成物で、手で編集しない（`folio inject --check` が差分を落とす。day-1 の `scripts/inject_check.py` は同じ導出の暫定版で、削除は別の便）。

<!-- constitution:begin -->
順位: 条どうしが衝突したら「網羅より揃い ／ 速さより黙らないこと ／ 賢さより戻せること」の順で解き、段どうしが衝突したら「絶対にやらない ＞ 確認してから ＞ いつも守る」の順で解く。

P-1.1: folio は文書を生成し、機械で検査し、結果を知らせるところまでを担う。

P-1.2: folio は要否・採否の最終判断を代行する機能を持たない。

P-2.1: 人が読むページはすべて 1 つの生成器から出力する。

P-2.2: 手書きのページを配信先と入口の導線に置かない。

P-2.3: 色・字の大きさ・余白の元の値（design token）は 1 か所で定義する。

P-2.4: 部品・図の型・密度 profile は閉じた一覧（部品目録）で持ち、追加には判断の記録を要する。

P-3.1: 機械で決定的に検査できる項目は床に置く。

P-3.2: 意味の検査（読みやすさ・忠実さ）は AI の天井に置く。

P-3.3: 床の合格を、完成や天井の合格として扱わない。

P-4.1: 検査・生成が実行できなかった結果を「異常なし」として扱わない。

P-4.2: 判定できないものは「まだ分からない」として表に出す。

P-5.1: 規則・閾値・型の一覧は型付きデータ（正本 YAML・rules 行・部品目録）に置く。

P-5.2: 文書と台帳（bd）からは、規則を id で参照する。

P-5.3: 文書の種類による違いは、汎用の検査と密度 profile のデータで表す。

P-5.4: 台帳（bd）はタスクと裁定の記帳先であり、規則を置かない。

P-5.5: 原則と裁定の正本は設計文書、機械が執行する規則の正本は型付きデータとし、置き場をこの 2 面に限る。

P-6.1: folio が生成する各文書の正本は YAML 1 file であり、人が読むページはそこから逐語で生成する。

P-6.2: 生成物を手で直さない。

P-6.3: 同じ内容を 2 つの面が持つとき、一方を正本とし、他方は導出する。

P-6.4: 2 つの面を人が書き、一致を検査で強制する設計を採らない。

P-7.1: 要件・条文・判断・受入基準の id を再利用・改番しない。

P-7.2: 廃止は状態（status）で表し、番号は空けたままにする。

P-8.1: 取り消しにくい判断（ADR）には、それを捨てる条件を同時に書く。

P-10.1: 検査は、生成側からも検査側からも独立した凍結 anchor（固定の fixture）を 1 本以上持つ。

P-10.2: 生成物どうしの突き合わせを唯一の合格判定にしない。

P-10.3: anchor が維持できなくなった検査の結果は「まだ分からない」に落とす。

P-11.1: 同じ種類の失敗が rules 行 R-7 の回数を超えたとき、自動の修正を続けず、止めて持ち主へ渡す。

P-12.1: 持ち主の承認は、rules 行 R-8 が指す 1 つの対話面を通ったものだけを受け取る。

P-12.2: 受け取った承認は、逐語と日付を添えて台帳の notes と文書の承認欄に記帳する。

P-12.3: 会話の記憶を承認の根拠にしない。

P-13.1: folio2 の開発を拘束するのは設計文書（design-intent）である。

P-13.2: 前の版（folio v1）を、受入の物差し役にも停止権の持ち主にもしない。

P-13.3: 設計文書の変更は、判断の記録か版付きの文書として残す。

P-13.4: 自分のコードの変更を自分の便で運ぶ運用（self-host）は、外部の利用者で受入が通った後に始める。

P-14.1: folio inject --write を実行したとき、憲法の前文と規範文を持つ条を CLAUDE.md の生成区間へ決定的に導出して書く。

P-14.2: folio inject --check は生成区間と正本の差分を検出し、差があれば失敗（非 0）で終える。

P-14.3: 生成区間の総バイト数は rules 行 R-2 以下に収める。

P-15.1: 自動で走る仕掛け（hook）を「守られる保証」として設計しない。

P-15.2: 編集の時点で止める仕掛けを持つときは、その判定の式を事後の検査が同じ関数で確かめる。

P-16.1: folio の設計判断を下す席は、その時点で最上位の AI モデルで動かす。

P-16.2: 道具（並列実行・便・作業者）の内側には最上位のモデルを求めない。

P-17.1: rules 表（R-n・D-n）の行の追加・変更は、裁定 id と時刻を行に付ける。

P-17.2: 裁定 id の無い rules 行の変更があったら、検査がそれを落とす。

P-17.3: 初版の行は、この憲法の発効の承認を裁定とみなし、発効時にその id と時刻を全行に付ける。

P-17.4: folio の振る舞いを縛る閾値行（deny 種別）の値を緩めるとき、A-2.3 の検証を前置する。

P-18.1: 編集が設計文書か rules と食い違うとき、その編集を編集の時点で止める。

P-18.2: 事後の検査を、編集の時点で止めることの代わりにしない。

P-18.3: 止める仕掛け（guard）は「開く／閉じる」の極性と「編集時／事後」の別を型で持ち、その一覧（極性一覧）を生成時に出す。

P-18.4: 編集の時点で止める guard が 1 本も無い構成なら、検査がそれを落とす。

A-1.1: 既存の文書やデータを消す、外へ出す、外部の道具や鍵を使う（課金を含む）操作を行うとき、実行前に rules 行 R-8 の対話面で持ち主の確認を得る。

A-2.1: 条文を改訂するとき、判断の記録と撤退条件を先に書き、持ち主の承認（逐語・日付・裁定 id）を得てから版を上げる。

A-2.2: 条文（id・見出し・規範文・段・縛る相手）と schema 節・前文が 1 文字も変わらない変更を改訂として扱わない。

A-2.3: 改訂の前に、その改訂が主張する利益を敵対的に検証し（grill）、記録を判断の記録に添える。

A-3.1: 外部ライブラリを増やす・減らすとき、予算（rules 行 R-6）と使ってよい条件（ライセンス）に照らし、持ち主の確認を得る。

A-4.1: folio が folio 自身の文書・コードを変える運用は、既定で許可する。

A-4.2: その操作が取り消せない（消す・出す・使う）とき、A-1 として持ち主に確認する。

A-4.3: 取り込み（merge）・公開へ出ない便・外部依存を増やさない変更は、A-4.2 の判定で「取り消せる」と扱う。

N-1.1: 操作が管理下の対象を回復不能に削除するなら、folio はそれを拒む。

N-1.2: 退役（廃止）は可逆な移動としてのみ行う。

N-2.1: 変更が、散文・記憶・会話にしか無い規則を持ち込むなら、それを規則として扱わない。

N-2.2: 変更が、散文・記憶・会話にしか無い規則を持ち込むなら、検査がそれを落とす。

N-3.1: 変更が規則の例外機構（無効化の旗・「今回だけ」の口）を足すなら、それを拒む。

N-4.1: 条文の改訂が、判断の記録・裁定 id・承認の逐語のいずれかを欠くなら、それを拒む。

N-5.1: 変更が文書の型ごとの AI 係（agent）や検査の観点（lens）を増設するなら、それを拒む。

N-6.1: 配信（serve）の接続先（bind 先）が tailnet の外なら、起動を拒む。

N-6.2: 配信の出力と、支度表・台帳の中身を、認証なしの公開ネットに晒さない。

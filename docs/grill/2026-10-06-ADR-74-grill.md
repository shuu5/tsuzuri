## 3. 移しの間（2 つの正本が並ぶ期間）と撤退条件

3-1（V）両形を持つ bead は断る（adr:15）。足りない所（I）:
- 同じ契約 id がノートの行と bead の欄 id に在る形を断る口が無い（2 の表）。
- 置き場の全部の行を読む口（live_row・review/index・spawn の table_rows・table/changed・review_ref）は v-bead-ledger か v-table-retire まで bead の契約を見ない（plan:26）。着地の rebase-stale-rows（`pipe/follow.rs:16-19`）は main に入った行しか見ないので、bead の契約が便の消した path を名指しても便を起こし直さない。決定 (2) の「便を起こす時に名を撃ち直す」で後から拾えるが、守りの時点が替わる事を記録が書かない。
- 切り替えから t-graph-bead の着地まで、board は bead の契約を描かない（plan:71 の順）。

3-2 撤退条件（adr:51-56）が測れる字か:
- (1)（V・重い）撃ち直しの「40% 以上」は、1-2 の測りでは切り替え後の見込みが 42〜43% で、**初日から当たる**。閾値を測りに合わせるか、指標を「範囲が設計の commit だけの載せ替えの回数」に替える。もう 1 つの「設計の commit が 10% を越える」は、切り替えの後も最大 21 日は生きたノートの行の直しと廃止の commit が続く（adr:20・plan:72）ので、窓を「最後のノートの廃止の後」にしないと移しの設計どおりの commit で当たる（I）。分母「初回の実装」の数え方（どの event を数えるか）が書かれていない（U）。
- (2)（I）「受付の断りの理由が bead の読みのもの」は、断りの語（v-bead-intake が足す 1 語・plan:58）を名指していない。「周」と「回」の別も無い。語を字で書けば測れる。
- (3)（U）「写しの外を読んだ例」を見つける機械が無い。審査の時に写しの digest と bead の今の digest を記録に 1 行書く、などの測る口を決めないと、誰も数えられない。
- (4)（V）21 日・生きたノートの本数は folio の床で数えられる。測れる。

## 4. acceptance に契約の 1 行を置く形の弱み

- 4-1 大きさ（V と U）: 2-2 の数のとおり acceptance 最大 19 KB・本文最大 49 KB。bd の欄の上限と Dolt の列の型は U（notes:33 のとおり bd create --help は起票の門が断った）。Linux の 1 引数の上限 128 KiB には収まる（I）。
- 4-2 読みの費え（I）: 列の候補を組むたびに開いた契約の bead の acceptance と本文を読む。上限が無いので bead の数×約 13 KB が毎周の台帳の読みに乗る。今も ledger-timeout が起きている（席の記憶）ので、上限が無い事と重なる。
- 4-3 digest（I）: 「acceptance と本文の字の digest」（adr:16・plan:49）の正規化（末の改行・空白の畳み・bd が返す時の整形）が書かれていない。bd が字を整形して返すと、直していないのに起き直るか、直したのに起きない。本文を書く機械（段 S3 の繋ぐ門が辺や印を本文に書くなら）が FAIL の便を起こし直す道にもなる（U・S3 の門の書き先）。
- 4-4 書きの原子性（I・U）: acceptance と本文を別の bd update で書くと、その間に列が写しを取ると、新しい acceptance と古い本文の組で便が起きる。1 回の bd update で両方を書けるかは U。書く間は bead を defer か hold に置く手順か、digest を受付の前に 2 度読んで同じ時だけ起こす手順が要る。
- 4-5 台帳の錠（I）: 契約の書きが日に約 50 件、台帳へ移る。問いの直後に台帳を書くと持ち主の答えが落ちた前例（席の記憶 answer-path-ledger-lock）があり、錠と順の決まりを v-bead-intake の前に決める必要がある。
- 4-6 本文の字の制限（V・I）: 今の導出は節の本文の二重引用符で落ちる（notes:15・derive rc 2）。bead の本文は自由な Markdown なので、写しを書く器が escape するか、preflight が断るかを決める（plan:44 は「書けない」とするだけ）。断るなら設計係の書きが今より窮屈になる。
- 4-7 履歴（U）: 「台帳の Dolt の履歴が代わる」（adr:73）は、欄ごとの差を読む命令を名指していない。

## 5. 承認の問い（question.md）

- 5-1（V・重い）q:23「撃ち直しも同じくらい減る見込み」は 1-2 の測りで誤り。q:22「493 本（40%）…これが無くなります」は、書きが台帳へ移ることと、112 本が直しである事を言わないので、仕事が 4 割減ると読める。
- 5-2（V）q:24 の 64/150 は、どの案でも先に流す v-pf-literal の利益で、甲を選ぶ理由にならない（1-3）。持ち主が「甲でないとこの利益が無い」と誤読しうる。
- 5-3（V）失う物の一覧（q:28・adr:27・plain の adr:63）に、散文の門（R-16）・章の上限（R-26）・計画だけの行の上限（R-33）・契約 id の重なりの照らし・移しの間の全部の行を読む照らしの空白が無い。
- 5-4（I）「削らない案を先に」に合わない。甲・乙・丙・丁はどれも上限を捨てる形か両方を書く形で、「甲に、開いた契約の bead の本数と本文の大きさの deny の行を足し、preflight と受付が数える」（上限を移す案）が無い。置かないなら、置かない理由を数で書く（今 open 3 本なので要らない、なら撤退の数えに本数を足す）。
- 5-5（V）q:28「約束は済めば bead が閉じるので積もりません」は保証の字に読める。今の事実（562 本中 open 3）と、上限が無い事を両方書く。
- 5-6（V）q:17「2〜3 週の見込み」の出所が記録に無い（adr の撤退 (4) は 21 日だけ）。案 戊が記録に在り問いに無い。平易さは概ね良いが、folio・board が言い換えなしで出る（q:28）。

## 6. 改めの字（amends）の誤り

- 6-1（V）**P-28.4 の strength が抜けている。** 今の P-28.4 は ubiquitous・must-not（constitution.yaml:587）。新しい字「…廃止の状態にし…残す」（adr:82）は event・must で、amends は pattern だけを替える（adr:84）。ADR-20 は pattern と strength を amends の欄に載せている（ADR-20 の amends）。folio の写しは規範文の 4 欄を持つ（`folio2/crates/folio/src/anchor.rs` の project の注「規範文の 4 欄」）ので、差との 1 対 1 の照らしで落ちる見込み（I）。`{"target":"P-28","field":"statements.P-28.4.strength","previous_text":"must-not","new_text":"must"}` を足す。
- 6-2（V）新 P-28.2「器は便を起こすときに…」は event の形だが pattern を ubiquitous のまま残す（notes:35 が迷いとして書く）。
- 6-3（V・I）規範文から上限が消えた後も、切り替えから t-derive-retire まで R-31〜R-33 が deny で効き、R-31 の note は条 P-28.3 を名指す（rules.yaml:112）。規範文の無い機械の規則が条の下に残る。退けまで効く事を規範文に 1 本残す（例「残る設計ノートは退けまで規則の表の上限で数える」）か、決定 (5) の字を条の字に上げる。notes:36 は「小さな食い違い」とするが、条 N-2.1 の逆向き（字の無い規則）である。
- 6-4（I）P-28 の mechanism（live: now・folio の床が P-28.2 を数える・constitution.yaml:593）は、新 P-28.2・P-28.3 では行 v-bead-intake・t-stop-preflight の着地まで偽になる。版を上げる commit で何を書くかを決定に書く（note は席に任せる・adr:87）。

## 7. 結論

**直してから問う。** D1 は決まっており、条を改める向き（甲）自体は支える。しかし主な数の主張（撃ち直しが 4 割減る）が測りで否定され、撤退条件 (1) は初日に当たり、amends に floor が落とす抜けがある。

直す字（重い順）:
1. adr:12・adr:27・q:23・notes:34 の「撃ち直しも同じ割合で減る」を消し、「載せ替え 339 回のうち範囲が設計の commit だけの物は 81 回（24%）・撃ち直しの率は 56% から約 42% の見込み」と書く。
2. 撤退 (1)（adr:53）の「40% 以上」を測りに合わせ直し、設計の commit の 10% の窓の始まりを「最後のノートの廃止の後」にする。分母「初回の実装」の数え方を書く。
3. amends に P-28.4.strength（must-not → must）を足す。P-28.2 の pattern を決める。
4. 失う物（adr:27・adr:63・q:28）に R-16 の散文の門・R-26・R-33・契約 id の重なりの照らしを足し、条 N-2 の機構の注の母集団の空を決定に書く。
5. 上限を移す案（開いた契約の bead の本数と本文の byte の deny の行・preflight と受付が数える）を削らない案として先に置くか、置かない理由を数で書く。
6. q:24・adr:12 の 64/150 を甲の理由から外し、「どの案でも先に流す行の利益」と分ける。
7. 移しの間に R-31〜R-33 を効かせる字を規範文に 1 本残す（6-3）。
8. 撤退 (2) の断りの語・(3) の測る口を字で名指す。
9. v-bead-intake の起草の前に照らす U: bd の欄の上限・1 回の bd update で acceptance と本文を書けるか・digest の正規化・台帳の錠の順。

## 2. 骨（席の提案）
**窓は使い捨て・相談は台帳に残る。** 窓の間を流れるのは id の指し示しだけで、中身は型付きの file が持つ。

| 物 | 何か | 置き場 |
|---|---|---|
| 相談 | 1 件の相談。問い・前提・望む形 | 台帳の bead（論点の子・label で見分ける） |
| 材料の束 | 相談の窓が最初に読む物。問い・読む file の一覧・導出グラフの近傍・関係する裁定 | `<state_dir>/consult/<相談 id>/bundle/`。形は folio の天井の束と同じ族（question・reads・sources・digest） |
| 要点の控え | 相談の途中で決まりかけた事を相談の窓が書き足す | `<state_dir>/consult/<相談 id>/notes.md` |
| 所見 | 相談の結論。型付き | `<state_dir>/consult/<相談 id>/finding-<n>.yaml` |
| 処分 | orchestrator が所見ごとに宣言（採る・一部採る・採らない と理由） | 台帳の notes の定型行。採った所見は orchestrator が repo の `docs/consult/` へ写す |

**所見の欄（型）**: 結論（1 文）・候補（2 つ以上と採否）・推奨・根拠の id・確かさ（verified / deduced / inferred / uncertain を主張ごとに）・持ち主に問うべき事・触る節点・使った model と effort・読んだ束の要約値。

## 3. 流れ
1. **開く**: orchestrator か持ち主（board の button）が相談を起こす。`tz consult open <論点>` が bead と束を作る。
2. **窓を起こす**: 器が tmux の別の窓（t3:consult）で Claude Code を起こす。model は持ち主が選ぶ（既定は rules 行）。SessionStart の hook が相談の id と束の path を注入する。
3. **相談する**: 持ち主と相談の窓が話す。相談の窓は repo と台帳を読み、repo の外の作業場で実験できる。要点の控えを書き足す。
4. **所見を出す**: 相談の窓が `tz consult answer` で所見を出す。口が欄を検めて置き場に書き、台帳に 1 行を足す。
5. **渡す**: orchestrator が待ちなら器の seat deliver が `consult:<id>-<n>` の 1 行を送る。考え中なら停止の hook が拾う。hook は所見の要約（上限つき）と path を注入する。
6. **処分する**: orchestrator が所見ごとに処分を宣言する。持ち主の承認が要る決定は、所見を材料に付けて裁定面に問いを置く。持ち主は面で答える。
7. **model を替える**: 窓を閉じて別の model で起こし直す。新しい窓は束と要点の控えと前の所見を読んで続ける。

## 4. 穴との対応
| 穴 | 塞ぎ方 |
|---|---|
| 1 型が無い | 所見は型付きの file。口が欄を検めて、欠けていれば受けない |
| 2 打鍵 | 送るのは器の固定の 1 行だけ。文は打たない。考え中の席には送らない |
| 3 手で写す | 原本は置き場の file。orchestrator は写さずに読む。採るときだけ repo へ写す |
| 4 記録が無い | 処分の無い所見は未反映の一覧に載る。不変条件で数える（候補 = 宙に浮いた所見 0） |
| 5 材料が無い | 束を機械が組む。導出グラフの近傍を使う（ADR-7 決定 (2) の材料と同じ関数） |
| 6 窓が割れる | 承認は裁定面だけ（P-12）。相談の窓の会話は承認にならない。所見の「持ち主に問うべき事」が面の問いになる |

## 5. 権能（rules 行の候補）
- 相談の窓: 読む（repo・台帳・state）・repo の外の編集（実験の作業場）・所見を出す口。
- 持たない: repo の編集・台帳の直の書き・回答・承認・go・便の起動。repo の書き手は orchestrator 1 席のまま。
- 却下: 相談の窓に設計文書の編集を渡す（書き手が 2 席になり衝突と事故の口が増える・scribe2 の却下と同じ）／相談の窓が orchestrator へ自由な文を送る（穴 2 の再発）／相談を orchestrator の subagent にする（持ち主と直に話せず、model を持ち主が替えられない）。

## 6. 連れて来る決め（この論点の後に要るもの）
1. **憲法 P-16 との食い違い**（verified = 条文）: P-16.1 は「設計判断を下す席は、その時点で最上位の AI model で動かす」。orchestrator を Opus 5.5 にし Fable を相談の窓に置くと、判断を下す席が最上位でなくなる。道は 2 つ = (ア) P-16 を「設計判断は最上位の model の所見を経て下す」へ改める（改憲 = 判断の記録と裁定・A-2・N-4）／(イ) t3 の orchestrator は最上位のままにする。P-16 の撤退条件（要件書の制約で model を名指す）も使える。
2. **器の対応**: 役割を 2 つ（orchestrator と consult）に戻す・窓の起動・権能の guard・所見の口。今の器（scribe2）は役割が 1 つ。合流の前に要るなら scribe2 の台帳に memo。口座の移り先の鍵は席ごとの model の窓で見る必要がある（今は orchestrator の model だけ）。
3. **当座の形**（器を待たない）: 持ち主が tmux の窓を手で開き、model を選んで起こす。相談の窓は所見を作業場の file に書く。持ち主が orchestrator に「相談 <id> の所見を読んで」と 1 行を打つ。型と置き場は本式と同じにして、渡す所だけ人の手。

## 7. 節点と辺（導出グラフへの足し方・候補）
- 節点の種類に「相談」と「所見」を足す。辺は `answers`（所見 → 相談）と `touches`（所見 → 触る節点）を使い回す。新しい辺の型は足さない。

## 8. 問い（1 問）
相談の窓を「相談は台帳の bead・材料は機械が組む束・結論は型付きの所見の file・窓の間を流れるのは id の 1 行だけ・承認は裁定面だけ・窓は使い捨てで model を替えられる」形にしてよいか。当座は器の対応を待たず、手で開いた窓と所見の file と持ち主の 1 行で運ぶ。推奨: この形。P-16 の扱い（§6 の 1）は次の問い。

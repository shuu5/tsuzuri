## 2. scribe2 席の推奨（討論の叩き台・採否は s3 で）
- **論点 A: 合流の形**: 1 workspace・crate 境界は folio / scribe / 面（surface）の 3 つ。境界の型は「設計ノートの行 → 契約（toml）」1 本。scribe2 の core（pipeline・seat・hook・rules・ledger adapter・fleet）は書き直さず持ち込む。folio v1 の HTML（憲法・ADR・research）を v2 形式へ移すのは v3 の中の別段。
- **論点 B: GUI = 「裁定を取る対話面」**: 口座と pipeline の管理は付随。本命は台帳（beads）・契約・裁定を持ち主に見せて合意を取る面。裁定は GUI が受け取り、UTC 分つきの id を機械が発行して台帳へ直接記帳する（今日の事故 = 裁定 id の分の写し忘れ・口座の自動移動の停止は、対話面が無いことの症状）。scribe2 には docs/design/dialogue-surface.md（次の 1 手が先頭・事実の 4 区分）が既に在り、その carrier になる。
- **論点 C: 表示面 = 1 つの表示 server + 2 種の client**: session は CLI で命令（この URL を出せ・viewport をこの端末枠に・reload）を送り、持ち主の browser は menu 無しの面として繋がって命令を実行する。remote / local の差は URL だけ（tailnet か localhost）。session の目（headless の browser・screenshot・DOM）は同じ server の別 client。スマホは 1 段目 = browser 内の端末枠（viewport・DPR・UA の模擬）、2 段目 = 本物の emulator の画面配信（要るときに足す）。app ごとに表示の仕組みを作らず、器の機能として 1 つだけ持つ。
- **論点 D（持ち主が最重要と名指し）: 技術スタック**。叩き台:
  - core は Rust のまま（scribe2 も folio2 も Rust・歯 1300 本超・憲法 C12「歯は Rust 1 framework」）。
  - 面の候補: (a) Rust の web server（axum 等）+ build 無しの HTML / JS（vanilla か小さな lib）＝toolchain 1 本・依存が増えにくい・UI の表現力に上限。(b) Rust backend + TypeScript frontend（Vite + React / Svelte）＝表現力・生態系・その代わり Node / pnpm の toolchain と supply-chain の面（憲法 A3 の依存の裁定・cargo deny 相当の npm 監査・C12 の「歯は 1 framework」と衝突するので憲法の改訂が要る）。(c) Tauri（Rust + webview）＝desktop 殻として軽く Rust と相性が良いが、要件は remote の tmux session でも使えることなので**browser で配る面が主・desktop 殻は後から任意**。(d) Electron ＝ Node の runtime を二重に持ち、remote の要件を満たさないので推奨しない。
  - 決め方の提案: 「面の複雑さがどこまで要るか」を先に grill（台帳の閲覧と裁定の入力・便と口座の一覧・表示面の制御 → この 3 つなら (a) で足りるか）。TS を採るなら「憲法 C12 の改訂」と「npm の依存の門」を同じ ADR で決める。
- **論点 E: 憲法**: scribe2 の C1〜C17 と folio2 の憲法（P / N / R）を 1 本に合流させる方法（どちらを母体にするか・矛盾の解消・凍結 anchor）。持ち主の裁定（A2）が要る。
- **論点 F: 台帳**: v3 の台帳（beads の prefix・epic）と scribe2 / folio2 の台帳の扱い（読み専用で残す・memo の持ち越し = s2-07l.214 / .590 / .604 / .608）。

## 3. 進め方（scribe2 席の提案）
- 1 論点 1 問・推奨 1 つで grill する（AskUserQuestion）。決まった語は `design-intent/vocabulary.yaml`、要件は `srs.yaml`、判断は `adr/` へその場で書く（persist-as-you-go）。討論の途中の記録は docs/ の下の markdown に置く（正本は YAML）。
- 読む面は `folio build --dir design-intent --out <配信先> --write` の HTML を tailnet-serve で出す（配信先は repo の外か .gitignore）。折々に `folio check --dir design-intent`。
- 論点の順: D（技術スタック）→ A（合流の形）→ C（表示面）→ B（GUI）→ E（憲法）→ F（台帳）。持ち主が「伝えきれていない要望」を持っているので、各論点の入口で「他に要望は」を 1 問挟む。
- この repo は private・remote 無し。公開は持ち主の裁定（A1）。口座の label と持ち主の逐語は tracked に写さない（逐語は台帳へ）。
